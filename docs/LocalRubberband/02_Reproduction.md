# LocalRubberband 2단계 — 러버 밴딩 재현 및 보정 중심 Baseline 분석

## 적용 범위
이 패치는 `LocalRubberband_Baseline_Addon.zip` 적용 이후에 사용한다. 프로젝트 루트에 덮어쓰고 에디터를 종료한 상태로 Development Editor 빌드 후 다시 실행한다. 기존 `Lv_LocalRubberband` 생성 및 PIE 설정은 1단계 README를 따른다. 원격 레벨, `Rubberband/`, `rb.*`, 기존 분석 스크립트는 변경하지 않는다. 신규 완화 알고리즘은 포함하지 않는다. 기존 레벨 생성이 안 됐다면 먼저 1단계 절차를 완료한다.

## 실험 순서
기존과 동일한 맵, BP 이동 설정, 입력 스크립트, 서버 설정 및 클라이언트 수(2)를 유지한다. 두 번째 클라이언트는 유휴 상태로 둔다. 기본 에디터 네트워크 에뮬레이션을 끄고, 움직이는 클라이언트 창에서만 명령어를 입력한다. 단일 프로세스 PIE, Play As Client. 각 명령은 이전 실행이 완료된 뒤 실행한다. 각 독립 반복은 fresh PIE로 동일 시작 위치에서 실시하는 것을 권장한다.

### 1. 정상 및 합성 보정 확인
```
lrb.Run N0 In 1
lrb.Run N0 In 1 200
```
`p.NetShowCorrections 1`은 선택 사항이다. 합성 오차는 실제 네트워크 현상이 아니며 주입 프레임과 교정 프레임을 구분한다. 교정이 없더라도 로그를 확인한다. 엔진 교정 정책에 따라 보정이 발생하지 않을 수 있다.

### 2. 기존 연구와 동일한 조건 (주 실험)
```
lrb.Batch N0,L100,L200,L300,J50-150,J100-300,L200-P3 In 3
```
기존 7개 설정값과 수신 방향을 유지한다. `3`은 한 조건에서의 자동 입력 3루프이며 독립 실행 3회가 아니다. 각 조건은 독립 반복 5회 이상을 초기 권장값으로 한다(확정 기준 아님). 기존과 같은 반복 횟수가 정해져 있다면 그것을 따른다. 기본 배치 순서와 설정은 변경하지 않았다. 결과는 원격 실험과 합치지 않는다.

### 3. 로컬 전용 추가 스트레스 실험 (별도 집계)
기존 7개 조건에서 교정이 드물거나 발생하지 않을 때 추가한다. 정상 상태에서 자동 입력 시작 약 0.75초 후 선택한 방향의 손실 설정을 100%로 바꾸고, 지정 시간 후 정상으로 되돌린다. 접속 종료가 아니다. 한 실행에서 한 번만 주입한다. B2000은 첫 직진 이후 정지 구간까지 걸칠 수 있다. 타이머 및 프레임 때문에 실제 설정 유지 시간은 목표와 달라질 수 있고, 이미 큐에 있던 패킷의 전달이나 실제 패킷 손실은 별도로 검증해야 한다.

| 추가 조건 | 연속 손실 목표 |
|---|---:|
| B500 | 500ms |
| B1000 | 1000ms |
| B2000 | 2000ms |

```
lrb.Batch B500,B1000,B2000 Out 1
lrb.Batch B500,B1000,B2000 Both 1
```
필요하면 `In`도 별도 실행한다. `Out`은 이동 요청, `In`은 승인/보정 수신, `Both`는 양쪽을 방해한다. 이 추가 조건은 원격 연구의 기존 7개 조건을 대체하지 않는다. 취소는 `lrb.Stop`(실행 클라이언트에서). 정상 종료/취소 시 원래 에뮬레이션 설정으로 복구한다. PIE 종료나 예상치 못한 엔진 장애 후에는 새 PIE를 시작하고 설정을 확인한다.

## 결과 분석
프로젝트 루트에서 실행:
```
python Scripts/Analysis/local_rubberband_events.py Saved/Experiments/LocalRubberband --output Saved/LocalRubberbandAnalysis
```
기존 `local_rubberband_metrics.py`도 계속 사용 가능하다. 새 분석 도구는 기존 1단계 로그와 호환되며 기존 원격 데이터를 읽지 않는다(입력 폴더를 LocalRubberband로 제한할 것).

- `runs.csv`: 완료 여부, 교정 콜백 수, replay 그룹, 연결되지 않은 콜백, 목표/관측 burst 시간, 샘플 기반 보정 주변 최대 위치 변화 등. `BurstObservedMs`는 로그의 설정 전환 시점 간격이며 실제 패킷 측정값이 아니다.
- `events.csv`: 첫 교정 콜백부터 replay 그룹 종료 후 250ms까지의 구간. Capsule, 기본 오프셋을 제거한 Visual, Camera의 연속 프레임 샘플 변화량과 샘플 간 속도 최댓값. `--tail-ms`로 변경 가능하나 비교 시 고정한다. 정상 이동도 포함한다.
- `UsableWindow=1`: 완료된 실행, 구간 전후 샘플 존재, 다른 교정 구간 및 합성 주입 프레임과 겹치지 않음, 유효한 연속 프레임 쌍 확보 및 구간 내 검출된 샘플 누락 없음. 이 조건을 충족하지 않는 구간도 진단용으로 저장하되 집계에서 제외한다. `WindowCovered`는 구간 양끝을 샘플이 감싼다는 뜻이지 실제 렌더 프레임 완전 기록을 보장하지 않는다.
- `CorrectionCallbacks=0`은 해당 로그에 native 교정 콜백이 없다는 뜻이다. 시각적 문제가 없었다는 뜻은 아니다. `UsableWindows=0`일 때 보정 주변 최대 이동 값은 빈 값으로 유지한다.
- 기존 Recorder의 `Visual`은 Mesh 기본 오프셋을 제거한 값이고, Camera는 PlayerCameraManager 캐시 샘플이다. 이 수치들을 실제 영상의 러버 밴딩 횟수나 화면상의 픽셀 변화로 단정하지 않는다. 영상 또는 프레임 계측 확인이 필요하다.
- `ReplayShiftCm`은 최초 교정 전 Capsule 위치와 재실행 이후 Capsule 위치의 차이로, 과거 서버 목표 위치와 현재 클라이언트 위치의 단순 차이를 사용하지 않는다.

## 검증 및 단계 완료 기준
1. UE 빌드 및 레벨 스폰 성공.
2. 정상 실행 로그의 `Complete=1`, 샘플과 입력 단계 확인.
3. 합성 또는 추가 손실 조건에서 native 보정 콜백 및 replay 기록, 실제 조작 화면에서의 후퇴/튐 확인. 합성 주입 자체는 러버 밴딩으로 계산하지 않는다.
4. 기존 7조건의 독립 반복 완료 및 동일한 측정 기준 적용. 교정이 없었던 실행도 기록한다.
5. 기존 원격 레벨 및 분석이 영향을 받지 않았는지 확인.

이 패치 제작 시 Python 합성 CSV 테스트 6개를 통과했다. UE 에디터/빌드/PIE 실행은 검증하지 못했고, 실험 결과 데이터도 아직 없다. 0.75초 트리거, 250ms 분석 구간, 추가 손실 조건은 초기 제안값이다. 다음 단계는 실제 `Saved/Experiments/LocalRubberband` 로그 및 필요하면 영상을 분석하여 완화 알고리즘의 설계 근거를 확보하는 것이다.
