# 06. 기준선 이후 무엇을 개발할 것인가

기준일: 2026-11-02 KST. **이 문서의 후보 선택·Warp·ReactionPlan·owner replay는 모두 신규 개발 제안이다.** 현재 실행 기능과 혼동하지 않는다. 원리의 출처는 [05](05_참고논문과개발연결.md), 순서와 완료 관문은 [07](07_단계별작업과평가.md)에 둔다.

## 1. 개발 목표와 효과를 나누는 방법

| 개발 축 | 만들 기능 | 검증 질문 |
|---|---|---|
| 안전 실행 | 경로 검사·안전 목표·제한된 Warp·벽 반응 | 같은 후보를 사용해도 무리한 이동 요구를 줄일 수 있는가? |
| 환경별 동작 선택 | 작은 후보 Library·특징/비용·결정적 선택 | 안전 실행만 하는 것보다 공간에 맞는 동작을 고르면 좋아지는가? |
| 행동 계획 공유 | 서버가 결정한 후보·목표·phase/revision 전달 | 같은 동작도 서버와 클라이언트가 같은 실행 제약을 쓰면 좋아지는가? |
| owner replay | 당시 계획 이력과 saved move 연계 | 피격자 소유 화면에서도 과거 이동이 올바른 계획으로 재현되는가? |
| 비용 검증 | 연결 전체 비용·calibration·효과 분리 | 개선이 추가 트래픽에만 의존하는가? |

먼저 기본 CMC 기준선을 확보한다. 이후 고정 후보의 안전 실행부터 만들고, 후보 선택과 공유를 차례로 추가한다. 동작을 전부 InPlace로 바꾸거나 반응을 늦추어 오차를 줄이는 방식은 행동 품질 지표에서 드러나게 한다.

## 2. 모듈과 파일 책임

아래 경로는 제안이다. 현재 공통 `Combat` 컴포넌트 위에 기능을 단계적으로 추가한다. 전용 `RootMotionHitWall` Character·레벨은 Lv_Jang 통합 과정에서 제거했다. Sharp 실험 연결은 `SharpCombatAdapterComponent`에 유지하며 Legacy의 별도 `SharpReaction` 전체 복제안을 동시에 생성하지 않는다. 아래 HitWall 명칭은 후속 연구의 제안 파일명이며 현재 존재하는 파일을 뜻하지 않는다.

Motion Warping 단계에서만 `.uproject` 플러그인과 Build.cs 의존성을 추가한다. GAS·Mover·PoseSearch 도입은 선행 조건이 아니다. 기존 Spline·Detector·Predictor·7개 전송 모드는 별도 실험으로 유지한다.

## 3. 후보 라이브러리와 궤적 준비

2026-11-08 추가: 관절/Root 추출·PELT 구간 분석·검토 전 Library/Warp 초안은 [08의 단계별 도구와 디버그 명령](08_관절추출_PELT_개발계획과테스트.md)으로 준비한다. 원본 분석 결과를 실제 I1 선택/I2 실행에 연결하는 관문은 별도로 유지한다.

첫 후보는 **BackLong / BackShort / InPlace / WallHit**다. 같은 피격 방향과 Skeleton으로 시작한다. 현재 단일 피격 에셋만으로 네 후보가 준비됐다고 보지 않는다. 확보·제작·리타기팅과 사용 권한 확인을 선행 작업으로 둔다.

| 후보 데이터 | 저장할 내용 |
|---|---|
| 고정 식별 | CandidateId, Montage, Section, LibraryRevision/Hash |
| 적용 제약 | 명중 방향·피격 자세·강도·MovementMode |
| 시간/공간 | 시간별 누적 root translation/rotation, 유효 구간, 기본 지속 시간 |
| 실행 제한 | 허용 이동 스케일·yaw·Warp Window·WallHit 전환 구간 |
| 품질 메타데이터 | 종료 자세·의도한 수직 이동·명시적 fallback 여부 |
| 시각적 검사 | 선택적 몸통/머리 bone proxy. 추가 blocking collision은 아님 |

Editor에서 지정 Section의 루트 궤적을 최초 30~60Hz로 추출한다. 실제 재생의 Section 연결·리타기팅·블렌드·Root Lock 영향을 반영했는지 무장애 CMC 이동과 비교한다. 허용 오차는 pilot에서 정하고 manifest에 기록한다. 에셋 또는 설정이 바뀌면 hash와 bake를 갱신한다.

현재 위치에서 후보 끝점만 검사하면 중간 충돌을 놓친다. 샘플 사이 모든 선분을 실제 scaled Capsule로 연속 sweep한다. 첫 버전은 지상 직선 translation·회전 고정 후보로 범위를 제한한다. 복잡한 곡선/회전 후보는 근사 오차를 확인한 뒤 추가한다.

## 4. 환경 위험 평가와 후보 점수

서버가 명중을 승인하면 다음 순서로 후보를 평가한다.

1. 실제 Capsule 크기·충돌 profile·시작 Transform·바닥을 확인한다. 초기 침투는 별도 상태로 보고한다.
2. 명중 방향·자세·MovementMode·유효 에셋 등의 hard constraint를 먼저 적용한다.
3. root-relative 궤적을 world-space로 변환해 각 선분의 첫 blocking hit, 접촉 시간, 남은 이동 거리를 수집한다.
4. 바닥과 수직 벽을 구분한다. WorldStatic 전체를 무시해서 바닥을 없애지 않는다.
5. 후보별 정상화한 특징을 Core 점수 함수에 넣고, 선택 이유와 탈락 이유를 남긴다.
6. 동일 비용이면 CandidateId 순서로 고른다. 모든 후보가 불가능하면 검증된 fallback으로 간다.

**프로젝트에서 제안하는 초기 비용식**은 다음과 같다. 논문의 식을 그대로 복제한 것이 아니다.

```text
J = wc × CollisionRisk
  + wz × UnexpectedRiseRisk
  + wp × PoseDiscontinuity
  + wk × KnockbackLoss
  + ww × WarpDistortion
```

| 항 | 초기 구현 | 확인할 한계 |
|---|---|---|
| CollisionRisk | 첫 장애물 여유·접촉 예상 구간·초기 침투 | 샘플링/쿼리와 실제 CMC 차이 |
| UnexpectedRiseRisk | 벽/낮은 장애물 법선·step-up 가능성 등 특징 | 실제 상승량을 정확히 예측하는 모델로 주장하지 않음 |
| PoseDiscontinuity | 처음에는 방향/자세 태그, 필요 시 관절 차이 | 단순 태그의 포즈 품질 한계 |
| KnockbackLoss | 요청 거리·방향 대비 후보의 이동 부족 | InPlace 남용을 낮은 오차로 보상하지 않음 |
| WarpDistortion | 원래 궤적 대비 scale/yaw 변화 | 허용 범위 밖은 점수보다 hard reject 우선 |

가중치·거리 정규화·tie-break·fallback을 tuning set에서 정하고 평가 전에 동결한다. 선택 시 후보 수·sweep 수·CPU 시간·원본 특징·점수·선택 이유를 `candidates.csv`에 남긴다. 공격 차폐용 Visibility 검사와 피격 경로용 충돌 채널은 목적이 다르다. 경로 검사 채널은 실제 CMC가 막히는 벽과 일치하는지 검증한다.

## 5. 안전 목표와 Motion Warping

충돌 검사의 첫 hit에서 **swept Capsule 중심**을 구하고 진행 방향 반대쪽으로 safety margin을 둔다. 벽 표면의 ImpactPoint를 Capsule 중심 목표로 사용하지 않는다. 이동 거리가 너무 짧으면 BackLong을 과도하게 압축하지 않고 Short/InPlace 등의 fallback을 쓴다.

처음에는 다음 조건만 지원한다.

- 평평한 지면, 정적인 벽, 직선 이동, 고정 yaw.
- 후보별로 검증된 Warp Window와 최소/최대 translation scale.
- Warp 목표를 설정한 뒤 변형될 전체 경로를 재검사.
- 최종 이동은 CMC swept movement가 처리. query 성공을 실제 충돌 해제 권한으로 사용하지 않음.

Warp 계산과 실행 경로의 오차가 크면 허용 범위를 줄이고 fallback한다. 캡슐의 Tick/OnRep Lerp·SetActorLocation으로 피격 이동을 덮어쓰지 않는다. MotionWarping과 Root Motion 변환 훅을 함께 쓰게 되면 delegate 소유·실행 순서를 먼저 확인한다. [엔진 기능 근거: Motion Warping](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-warping-in-unreal-engine).

## 6. 접촉과 벽 반응 상태 머신

```text
Idle → Planned → Playing → Recovering → Idle
                    ↓
                WallContact → WallReaction → Recovering
모든 활성 상태 → Cancelled / Replaced
```

| 상태 | 처리 |
|---|---|
| Planned | ID/목표/제약/에셋 검증, Warp target과 입력 잠금 준비 |
| Playing | 지정 후보를 한 번 실행. Root Motion 요청과 CMC 실제 이동 분리 기록 |
| WallContact | 실제 blocking hit + 요청 대비 이동 부족 관찰. 중복 callback 방지 |
| WallReaction | 벽 안으로 계속 이동을 요구하지 않는 Section/Montage로 전환 |
| Recovering | 제어 복귀·경직 해제·종료 이유 게시 |
| Cancelled/Replaced | 이전 ID의 타이머·Notify·종료 콜백을 무효화 |

접촉 진입/해제에는 짧은 hysteresis를 두고 값은 동결한다. 단순 StopMovementImmediately가 다음 프레임 Montage Root Motion까지 멈춘다고 가정하지 않는다. 우선 검증된 Montage 전환을 사용하고, 실패가 남을 때만 CMC 내부의 추가 변위 제한을 검토한다.

권위 damage·stun·게임 상태 전환은 서버만 결정한다. **비교군의 LocalPlan에서는 실행 목표·벽 반응 판단을 각 실행 지점에서 계산하고, SharedPlan에서는 서버의 목표·phase 결정을 따른다.** 로컬 시각 상태가 별도 서버 명중/피해 사건을 만들지 않는다. 충돌 profile·입력 잠금·fallback 규칙과 코드는 군별로 동일하게 둔다.

## 7. 서버 행동 계획 공유

`FSharpReactionPlan`은 위치를 강제로 덮어쓰는 두 번째 이동 복제가 아니라 **CMC가 실행할 행동 의도**다. 최초 계약은 충분한 정밀도로 만들고, 비용 측정 후 필요한 직렬화·양자화를 추가한다.

| 필드 묶음 | 목적 |
|---|---|
| SchemaVersion, RunId, TrialId, Generation | 버전·다른 실행·재생성 Actor 데이터 배제 |
| ReactionId, PlanRevision | 새로운 피격과 같은 피격의 목표/상태 변경 구분 |
| CandidateId, SectionId, LibraryRevision/Hash | 동일 에셋·구간 확인 |
| Phase, PhaseRevision, PhaseStartServerTime | Playing/WallReaction/종료 등 최신 상태 재구성 |
| HitServerTime, DecisionServerTime | 명중 시각과 계획 완료 시각 구분 |
| ServerPlanOrigin, TargetPosition, TargetYaw | 평가 기준과 실행 목표 |
| PlayRate, AllowedScale, MovementPolicy | 재생/이동 제약 |
| ContactId/ObstacleId/Normal, Expiry, EndReason | 필요한 접촉 문맥·만료·종료 처리 |

피격 Actor의 단일 RepNotify struct를 기본 전달 수단으로 제안한다. candidate/phase/target을 개별 OnRep 순서에 의존해 조립하지 않는다. 수신 시 문맥·ID·revision·expiry·library를 검증하고 중복이면 재생을 재시작하지 않는다. 이전 계획의 콜백은 새 계획을 끝내지 못한다.

종료/취소 상태도 일정 시간 유지한다. 모든 중간 transition을 반드시 수신한다고 가정하지 않고 최신 상태로 복구할 수 있게 한다. 필요 시 owner 시작 RPC를 추가할 수 있지만 property와 같은 ID로 deduplicate하고 모든 군에서 전달 방식을 고정하며 비용을 센다.

늦은 수신의 시각적 pose seek와 실제 Root Motion catch-up은 다른 처리다. `Now-StartTime`만큼 무조건 Montage를 seek하거나 지난 변위를 현재 위치에 한 번에 더하지 않는다. native correction/fixup과의 조합을 검증한다. 클라이언트가 아직 모르는 외부 피격의 최초 전달 지연은 공유 이후의 지속 불일치와 별도 지표로 둔다.

## 8. 소유 플레이어 피격과 replay

AI 기준선이 안정된 뒤 Dedicated Server + Client 2개로 확장한다. Client A는 공격자 소유·피격자 관찰, Client B는 피격자 소유·공격자 관찰을 맡는다. 별도 possession/입력/고정 카메라 설정이 필요하다. 두 클라이언트 역할을 바꿔 확인한다.

1. 먼저 소유 피격자의 **기본 Montage Root Motion saved move·correction**을 계측한다. 기본 엔진 경로를 임의로 대체하지 않는다.
2. 새 목표·제약이 replay에 필요하면 `FSavedMove_Character` 파생형에 당시 ReactionId/revision·목표·phase 참조를 저장한다.
3. 설치 엔진의 `SetMoveFor`/`PrepMoveFor` 시그니처와 복원 시점을 확인한다. 계획이 다른 move를 잘못 합치지 않도록 `CanCombineWith`를 검사한다.
4. 서버가 move를 평가할 때 필요한 값만 `FCharacterNetworkMoveData`/Container에 추가한다. client move timestamp와 server world time을 같은 값으로 취급하지 않는다.
5. 서버는 client가 보고한 ID/revision을 승인된 계획 이력과 대조한다. 최신 목표를 모든 과거 move에 적용하지 않는다.
6. saved move 보존 기간을 덮는 bounded plan history를 유지한다. 이력 만료·늦은 revision·미인지 피격을 명시적으로 처리하고 native correction으로 수렴시킨다.
7. 원래 실행과 replay 샘플을 구분한다. 재시뮬레이션의 Notify·접촉으로 damage·명중·벽 사건이 중복 발생하지 않게 한다.

서버 사건 시각, owner 수신, 첫 적용 move timestamp, Montage track, correction 수신, replay 후 현재 Capsule 변화가 필요하다. observer의 SmoothCorrection과 owner correction RPC 횟수를 합산하지 않는다. [기반: CMC 네트워크 이동](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine).

## 9. 계측 확장과 실패 처리

기준선 파일에 추가로 `candidates.csv`, `plans.csv`, `rootmotion_samples.csv`를 제안한다. 공통 키에 PlanRevision·LibraryRevision·phase·replay 여부를 추가한다. 원본 Root Motion 요청량, 실제 Capsule 변위, 표시 Mesh 이동을 구분한다.

정상 충돌로 이동량이 감소하거나 회복에 실패한 것은 결과다. 기술적 실행 실패와 구분한다. asset/schema 불일치, 누락된 핵심 기록, 접속 실패는 invalid 사유와 횟수를 남긴다. 관통·상승이 많은 Trial을 제외해 성능을 좋게 만들지 않는다.

설치 엔진 소스로 override 가능한 훅을 확인하고 Super를 유지한다. `OnRep_RootMotion` 같은 이름의 함수를 단순히 추가해 실제 엔진 수신 경로를 가로챘다고 가정하지 않는다. 관찰한 root 상태 변경은 패킷 수신 횟수와 구분한다. 내부 경로의 정확한 분리는 Networking Insights나 별도 엔진 계측으로 검증한다.

## 10. 후속 확장 순서

첫 주 비교가 끝난 뒤 **접촉 진입/해제 갱신·짧은 Burst**, 비스듬한 벽·코너·연속 피격, 움직이는 문·다른 Enemy 순으로 확장한다. 동적 장애물은 과거 move의 환경과 현재 환경이 다르므로 장애물 transform/contact 이력 또는 그 한계를 명시해야 한다. 전체 월드 rollback을 구현하지 않았다면 정적 벽 결과와 합쳐 일반화하지 않는다.

최초 개발에서 제외할 범위는 신경망 신규 학습, 전체 Motion Matching 교체, GAS/Mover 전환, 래그돌·공중 피격, 전체 물리 월드 rollback이다. 현재 증상의 원인을 확인한 뒤 필요한 확장만 추가한다.
