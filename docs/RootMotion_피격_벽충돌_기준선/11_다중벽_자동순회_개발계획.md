# 11. YHJ 다중 벽·경사면 자동 순회 비교 개발계획

작성: 2026-11-09 KST. 상태: **현황 조사 완료 / 다음 개발 명세. 아래 신규 명령·컴포넌트·실험 Profile은 아직 구현하지 않았다.** 이번 작업은 문서 작성과 읽기 전용 조사이며, 게임 코드·맵·태그를 변경하거나 피격 실험을 실행하지 않았다.

후속 구현: 2026-11-09 태그 adapter 기반 Tour/Stations와 로컬 카메라·Pause/Resume를 구현했다. 아래 내용은 원래 설계이며 실제 구현된 인자와 후속 범위는 [12. 순회 실행](12_다중벽_순회_실행.md)을 따른다.

## 1. 방향 검증과 이번 개발의 목표

**여러 지형에서 같은 피격을 반복하고 원본과 보정을 눈으로 비교하는 방향은 적절하다.** 한 정면 벽에서 확인한 급정지 완화가 비스듬한 벽에서도 유지되는지, 낮은 턱·걸을 수 있는 경사에서 오히려 동작을 훼손하지 않는지 확인할 수 있다. 기존 station 순회와 서버 피격 인터페이스를 재사용할 수 있어 새 전투 시스템을 만들 필요도 없다.

다만 벽을 피하기 위해 멈추는 동작, 경사면을 올라가는 동작, 벽에 부딪히는 동작은 목표가 다르다. 모든 지형에서 충돌·높이 변화가 0이면 성공이라고 평가하지 않는다. 이번 목표는 **하나의 디버그 입력으로 명시적으로 등록한 모든 지점을 순회하며, 같은 위치·카메라에서 Off와 선택한 보정을 연속 재생하고, 적용·원본 유지·fallback·배치 실패를 구분해서 보여주는 것**이다.

이번 단계에서는 Root Motion solver, IK, 포즈, 재생 속도, 네트워크 prediction을 동시에 변경하지 않는다. 먼저 실험 도구를 신뢰할 수 있게 만든 뒤 결과에 따라 보정 알고리즘을 개선한다.

## 4. 지형별 비교 목적과 사전 검사

### 4.1 서로 다른 두 각도와 거리

- 벽 입사각: 수평 후퇴 방향 `d`와 접촉 법선의 수평 성분을 사용한 `acos(clamp(dot(-d, normalize(nXY)), -1, 1))`. 0도는 정면 접근이다. 수평 법선이 0이면 N/A.
- 표면 경사각: `acos(clamp(n.Z, -1, 1))`. 바닥은 0도, 수직 벽은 90도다. 아래를 향한 면 등은 별도 분류한다.
- `requested_gap_along_retreat_cm`: 후퇴 방향 Capsule sweep를 기준으로 설정한 거리. 사선 벽의 최단 수직 거리와 같다고 가정하지 않는다.
- `measured_gap_along_retreat_cm`, 목표/실제 최단 여유, runtime plan budget은 각각 기록한다. 기존 probe의 2cm 축소 Capsule 거리와 full Capsule 거리도 구분한다.

### 4.2 평가 분류

| 분류 | 적용 대상 | 관찰할 것 | 성공으로 오해하면 안 되는 것 |
|---|---|---|---|
| `StopBeforeSurface` | Wall, Wall45의 초기 목표 | 충돌 급정지·옆 미끄러짐·발 디딤·도달 거리 | 짧게 움직여 충돌이 사라진 것만으로 자연스러움 통과 |
| `TraversalDiagnostic` | Ledge30/60, Slope30/55의 초기 분류 | step-up/바닥 추종/떠오름/발 접촉과 보정의 상호작용 | 의도된 지형 상승을 비의도적 상승으로 집계 |
| `ContactReaction` | 후속 벽 충격 연출 | 접촉 시점과 전용 동작 연결 | 현재 기능이 전용 벽 충돌 포즈를 만든다고 주장 |

TraversalDiagnostic도 전체 관찰 순회에 포함한다. 기본 피격은 재생 가능하되 solver fallback과 지형 지원 범위를 함께 표시한다. 지형 진입을 막는 것이 실제 게임 의도라면 해당 station을 명시적으로 StopBeforeSurface로 바꾼다. 한 결과를 두 목적의 성공으로 혼합 집계하지 않는다.

사전 검사는 다음 순서로 수행한다.

1. 예상 지점 목록과 실제 로드 목록을 대조한다. 미로드/없는 참조/중복 ID/비활성 레거시 태그를 모두 표시한다. 새 Profile 등록을 제외하고 발견된 `xHitWall_`를 조용히 활성화하지 않는다.
2. 대상 Enemy/Attacker, Montage, Library/Policy, 컴포넌트, source/policy 식별자, draft 여부를 고정한다. 먼 station으로 이동한 뒤 가까운 Enemy를 다시 선택하지 않는다. 맵에 있는 여러 Enemy·Spline·ImpulseVolume이 간섭하지 않는지 확인한다.
3. 마커 기준 바닥과 walkability를 확인하고 실제 시험 위치를 계산한다. Enemy와 Player의 각 위치에서 바닥, Capsule overlap, standoff 공간, 지원면을 별도로 검사한다. 설정 숫자보다 실제 CMC floor clearance를 사용한다.
4. station이 가리킨 장애물과 실제 첫 blocking Actor/Component를 대조한다. 다른 벽·발판·Pawn을 맞혔다면 잘못된 실험으로 표시한다. 모서리에서는 첫 면과 후속 면을 모두 기록한다.
5. 해당 지점을 로드하고 지상 정착·위치 안정 후 실제 gap, CMC의 `IsWalkable(Hit)`, MaxStepHeight, CanCharacterStepUpOn, WalkableSlopeOverride, 바닥 법선을 기록한다. 이름만으로 30/55도 및 step 가능 여부를 정하지 않는다.
6. 조건이 불가능하면 해당 station×gap만 `Skipped` 처리하고 이유를 보존한다. 전체 지점 사전 검사 결과를 먼저 보여준 뒤 유효 조건을 순회한다.

걸을 수 있는 경사 여부는 캐릭터와 물리 컴포넌트의 slope override 영향을 받는다. 단순한 전역 각도 비교를 완전한 walkability 판정으로 사용하지 않는다. [Epic Walkable Slope](https://dev.epicgames.com/documentation/en-us/unreal-engine/walkable-slope-in-unreal-engine)

## 5. 제안하는 구현 구조

다음 이름은 제안이며 구현 시 주변 코드 스타일에 맞출 수 있다. 기존 여섯 좌표·Actor 이름·각도를 C++ 분기로 하드코딩하지 않는다.

|---|---|---|
| 실험 정의 | `UReactionExperimentProfile` DataAsset | 맵, 대상/공격자 참조, Library/Policy, 명시적 station ID·marker·예상 장애물·평가 목적·카메라 설정. 첫 YHJ Profile에 위 6개 등록 |
| 지점 검사 | `UReactionStationComponent` 또는 공통 station resolver | 기존 TargetPoint를 adapter로 읽을 수 있게 함. Editor actor path를 PIE에 그대로 쓰지 말고 stable ID와 월드별 resolver로 대응 |
| 공통 실행 | 기존 `UHitWallProbeSubsystem` | audit→load→place→settle→hit→tail→next. 기존 Compare/Run과 로직 중복 최소화 |
| 관찰 화면 | 로컬 `UReactionTourViewComponent` | station 상대 카메라·HUD·진행 상태. 피격·이동·계획의 authority를 소유하지 않음 |
| 기록/보고서 | 기존 Probe·ReactionWarpArtifacts·분석기 | station/trial/role 식별, 상태·사유·지형·실제 궤적 기록. Saved task README부터 생성 |

Profile의 여섯 항목과 월드 등록 수를 비교해 ‘전체’의 의미를 고정한다. World Partition은 발견 당시 로드된 Actor만으로 전체를 정의하지 않는다. 필요하면 manifest 기반 로드/streaming source를 사용하고 readiness timeout을 둔다. [Epic World Partition Load Actors](https://dev.epicgames.com/documentation/unreal-engine/BlueprintAPI/WorldPartition/LoadActors?lang=en-US)

## 6. 디버그 입력 계약 — 아래 신규 명령은 아직 실행 불가

명령은 한 줄씩 입력하고 Enter를 누른다. 신규 명령은 authority game/PIE 월드를 명시적으로 요구한다. Client 창이나 일반 Editor 월드에서 임의 서버를 추측해 실행하지 않는다. profile/대상/모드/거리 등의 인자는 실행 전 검증하고 오류 시 상태를 바꾸지 않는다.

| 신규 명령 | 동작 |
|---|---|
| `ReactionWarp.Stations profile=<Profile경로>` | 여섯 지점·태그·예상/로드 수·바닥·장애물·지원 범위를 감사. 피격 없이 검사 결과와 task 경로 표시 |
| `ReactionWarp.Tour profile=<Profile경로> mode=Off baseline=None gaps=120,100,80 reps=1` | 기본 충돌만 전체 지점에서 관찰 |
| `ReactionWarp.Tour profile=<Profile경로> mode=Uniform baseline=Off gaps=120,100,80 reps=1 AllowDraft=1` | 지점·거리마다 Off→Uniform 연속 재생 |
| `ReactionWarp.Tour profile=<Profile경로> mode=MultiPhase baseline=Off gaps=120,100,80 reps=1 AllowDraft=1` | 지점·거리마다 Off→MultiPhase 연속 재생 |
| `ReactionWarp.Tour profile=<Profile경로> mode=MiddleOnly baseline=Off gaps=120,100,80 reps=1 AllowDraft=1` | 동일 조건에서 가운데 구간만 보정. 용량 부족을 성공으로 표시하지 않음 |
| `ReactionWarp.Tour profile=<Profile경로> mode=MultiPhase baseline=None gaps=100 reps=1 AllowDraft=1` | 선택한 보정만 모든 등록 지점에서 관찰 |
| `ReactionWarp.TourPause` / `ReactionWarp.TourResume` | 현재 피격과 tail을 끝낸 뒤 다음 trial 진행만 일시 정지/재개 |
| `ReactionWarp.TourReplay` | 현재 진행 중이면 끝난 뒤 마지막 station/gap의 비교 쌍을 초기 상태부터 재생. replay 별도 ID |
| `hitwall.Stop` | 순회 중단·미실행 trial 취소 기록·상태 복원. 기존 명령 재사용 |

`<Profile경로>`는 개발 단계에서 생성할 실험 DataAsset 경로다. 현재 존재하는 Asset 이름처럼 안내하지 않는다. mode=Off/baseline=Off는 중복 실행하지 않는다. 알 수 없는 인자, 빈 목록, NaN/음수 거리, 중복 station ID, 전체 trial 수 상한 초과는 거부한다. 시험 상한에는 station 수와 baseline을 포함한다.

관찰 순서는 **station → gap → 반복 → Off/선택 모드**로 한다. 정량 측정 모드에서는 순서 효과를 줄이기 위해 순서를 교대하거나 seed가 기록된 순열을 사용할 수 있다. 첫 관찰은 6지점×3거리×2모드×1회=36개 예정 trial이다. Skip도 36개 예정 항목 중 하나로 남겨 ‘모든 벽’의 누락을 숨기지 않는다.

기존 명령은 별도로 유지한다. `hitwall.Run stations gaps=40 warp=0,1 reps=1`은 **현재 태그 기준 Ledge30의 Legacy 비교**이고, `ReactionWarp.Compare`는 **현재 위치의 네 모드 비교**다. 둘을 새 전체 순회 기능처럼 설명하지 않는다.

## 7. 자동으로 보여주는 화면과 상태 복원

- 시작 전 예상 station 수, 실행/진단/skip 수와 이유를 출력한다. 매 trial에 station ID, 측정 각도, 요청/실측 gap, 모드, 반복 번호, 진행률을 고정 HUD로 표시한다.
- 피격 직후 `Planned`, `Unmodified`, `Fallback + reason`을 표시한다. 준비 거부·timeout·skip은 별도 색상/문구로 보여준다. `Completed`는 재생 종료를 뜻하며 자연스러움 합격이 아니다.
- 각 지점에서 피격자·벽·발이 함께 보이는 측면 또는 3/4 카메라를 사용한다. Profile의 station 상대 transform을 사용하고, 같은 비교 쌍은 같은 카메라/FOV/거리로 고정한다. 캐릭터를 따라가는 카메라로 급정지를 가리지 않는다.
- 기본 게임 재생은 1×. 피격 전 안내 대기와 종료 후 관찰 시간을 설정으로 제공한다. 슬로모션이 필요하면 녹화 재생에서 제공하고, 전체 world dilation으로 실험 물리를 바꾸지 않는다.
- 실제 UE 화면을 자연스러움 판단의 주 자료로 사용한다. 기존 HTML 원본 골격 재구성은 runtime IK·블렌딩·다중 벽 표면을 그대로 재현하지 못하므로 보조 수단이다.
- 시작 때 Actor transforms, 변경할 movement/AI/input 상태, mode/enable/draft, camera view target/control rotation/FOV, probe/label/FPS를 저장한다. 끝·사용자 stop·실패·Actor 소멸·world 종료에서 변경한 항목을 복원한다. World가 사라진 뒤 객체 접근은 하지 않는다.
- 직접 이동/공격 입력과 시험 대상의 자율 이동이 시험을 교란하지 않도록 기존 제어 인터페이스를 통해 일시 중단하고, 입력 잠금 누적 횟수와 원래 상태를 보존한다. 전체 월드를 정지하거나 관련 없는 Actor를 제거하지 않는다.
- 첫 구현은 Standalone 및 Listen Server의 로컬 관찰 화면을 대상으로 한다. 서버가 배치·피격·계획을 결정한다. 원격 클라이언트 카메라 자동 이동은 후속 기능이며, 추가 시 별도 네트워크 검증을 한다. 기존 AI plan 복제를 소유 플레이어 prediction 지원으로 표현하지 않는다.

### 8.2 평가할 것

1. Off 대비: 충돌 전후 속도 단절, 후퇴가 막힌 구간, 접지 기준 발 이동, sideways drift, 도달 거리, 벽 여유, 실제 화면 선호를 비교한다.
2. Uniform 대비: 같은 실제 도달 거리·재생 시간에 가까운 조건에서 초기 반동·발 디딤·회복을 더 잘 보존하는지 확인한다. 거리가 다르면 그 차이를 함께 보고하고 우월성 결론을 제한한다.
3. 경사·턱: 지형의 바닥 높이 상승과 Capsule 바닥의 지면 이탈을 분리한다. 지형을 따라 올라간 Z 전체를 비의도적 상승으로 점수화하지 않는다. 벽 hit뿐 아니라 지면/장애물 접촉을 따로 기록한다.
4. foot reference: 무장애 Off 및 같은 에셋/재생 조건으로 참조를 만들고 사람이 발 고정 구간을 검토한다. 지면 근처의 발 이동 전체를 미끄러짐으로 단정하지 않는다. runtime trace 지표와 기존 reference 기반 지표를 구분한다.
5. 속도: 같은 샘플 시간 기준으로 비교하고 시간 반올림·프레임 간격을 기록한다. 인접 속도 감소, 가속도, jerk를 혼용하지 않는다. 보정 때문에 전체 이동량/속도가 줄어든 영향도 함께 해석한다.

기존 완료 실행의 80cm 조건에서 다구간은 Off보다 급격한 인접 속도 감소가 약 45~59%, 접지 trace 중 발 이동 합계가 약 7~8% 작았다. 그러나 이동 거리도 약 28% 작았고 Uniform과 차이가 작았다. 이 결과는 위 여섯 지형의 개선 증거가 아니다. 이전 데이터는 최종 blend 참조 수정 전이므로 최신 코드로 다시 측정한다.

80cm 조건의 계획 목표 70cm는 최소 용량 68.49cm에 가까워 구간별 분배 여지가 약 1.51cm뿐이었다. 120/100/80cm gap은 중간 압축을 탐색하는 시작값이며, 사선·경사에서는 실제 budget이 다르므로 결과에서 확인한다. 250cm 무장애 기준과 40/10cm 용량 부족 조건도 별도 회귀 세트로 유지하되, station 전체를 무효화하지 않는다.

## 9. 개발 순서와 완료 기준

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| T0 현황 고정 | Profile·여섯 station·대상·에셋 연결, 최신 다구간 코드/빌드 확인 | 같은 Profile에서 예상/로드/검사 결과 6개가 모두 이름으로 보임. 비활성 레거시 태그 및 잘못된 참조를 명확히 표시 |
| T1 배치 검사 | 조건별 floor/overlap/장애물/실측 gap·streaming 검사 | 유효 조건은 반복 가능한 시작점. 불가능한 큰 gap이 가능한 작은 gap을 제거하지 않음. 두 Pawn 모두 안정된 상태에서 시작 |
| T2 자동 순회 | 공통 runner에 단일 선택 모드·baseline·station 순서 연결 | 36개 예정 조건의 완료/skip/실패 수 합계 일치. fallback/원본 유지 구분, 취소·재실행·복원 확인 |
| T3 관찰 화면 | 로컬 카메라·HUD·pause/replay | 각 벽과 발을 볼 수 있음. 비교 쌍의 카메라/초기 상태 동일. 입력과 카메라가 종료 후 복원 |
| T4 측정/보고서 | station-aware schema·발 참조·영상/평가 연결 | 단일/두 모드와 여러 지점 지원. 거리/plan/CMC 차이 표시. 기존 단일 지점 자료도 읽거나 명시적으로 버전 안내 |
| T5 실제 평가 | 6개 지점 관찰 후 각 유효 조건 3회, 필요한 거리 보강 | 환경별 개선/동등/악화/판단 불가를 보고. 자연스러움 합격을 기술 자동검사와 분리 |
| T6 선택적 네트워크 | 실환경 observer 또는 새 tour 동기화 검증 | 변경 시 authority/owning client/remote client 영향 확인. 같은 ReactionId/plan과 재생 종료 검증. owner replay는 별도 |

검증은 변경 범위에 맞는 Editor 빌드와 실제 렌더링 Standalone 실행을 필수로 한다. 자동 회귀는 지점 누락, 중복 ID, invalid mode/NaN, 한 gap만 불가능, 예상과 다른 장애물, 초기 overlap, slope/step 분류, timeout, 중간 취소·대상 소멸, 원상복구 및 report 그룹 충돌을 다룬다. Root Motion 연결을 변경하면 기존 수치/블렌딩 회귀도 수행한다. 복제 동작을 변경하면 실제 멀티플레이 검증이 필요하다.

최초 구현의 종료 기준은 ‘모든 지형이 자연스럽다’가 아니라 **전체 여섯 지점을 빠짐없이 확인하고, 사용자가 같은 조건의 원본/보정을 자동으로 비교하며, 적용되지 않은 보정을 성공으로 오해하지 않는 상태**다.

## 10. 결과에 따른 다음 개선 결정

- 중간 압축에서도 MultiPhase가 Uniform보다 낫지 않으면 PELT 경계·보존 가중치·접지 구간 정책을 먼저 재검토한다. solver 복잡도를 바로 늘리지 않는다.
- 실제 이동이 계획보다 크게 짧으면 원본 추출/블렌드/보정/CMC 단계의 차이를 먼저 해결한다. 이번 70→약57cm 차이를 지형 이점으로 해석하지 않는다.
- 보정은 적용되지만 발 디딤이 악화되면 접지 구간 보존·짧은 동작 선택을 우선 검토하고, 필요할 때 포즈/IK 보정을 별도 실험으로 추가한다.
- 낮은 턱·완만한 경사에서 Off가 더 자연스럽다면 surface classification과 traversal 허용 정책이 필요하다. 모든 접촉을 정지 목표로 바꾸는 정책을 유지하지 않는다.
- 가까운 벽에서 용량 부족이 반복되면 Short/InPlace/WallReaction 후보 선택을 후속 개발한다. 최소 배율을 무조건 낮춰 성공률만 높이지 않는다.

## 11. 이번 문서 작업에서 수행한 검증

- 로컬 브랜치/원격 추적 ref 및 tree 차이, station 명령·실행·복원·환경 검사·Probe·보고서 호출 경로를 읽었다.
- 별도 commandlet로 맵을 읽어 40개 Actor와 41개 descriptor를 대조했고 여섯 마커/장애물 후보를 확인했다. 첫 실행은 GameFeatureData 설정 오류로 exit 1이었으나 inventory 추출은 완료됐다. 기존 `-CustomConfig=AnimationAnalysis`를 사용한 재실행은 **exit 0, 0 errors/0 warnings**였다.
- 조사 프로세스는 에셋 저장·PIE 실행을 하지 않았다. 현재 에디터의 맵을 변경하지 않았다.
- 빌드·피격·카메라·자연스러움·네트워크 검증은 이번 문서 작업에서 실행하지 않았다. 게임 코드 변경이 없으며 위 T0~T6의 다음 개발 검증으로 남긴다.
