# 03. 측정과 완료 기준

2026-11-02 KST 갱신. 아래 CSV·계측 훅·자동 완료 검사는 **앞으로 구현할 정량 기준선의 요구사항**이다. 현재 기능 검사 로그와 구분하며, 구현 상태는 [01](01_구현계획.md)을 따른다. 기존 3종 공격 중 정량 실행은 Attack 01 한 번으로 고정하는 진입점을 추가한다.

## 1. 무엇을 문제로 구분할 것인가

| 관찰 | 해석할 영역 |
|---|---|
| Standalone/서버 Capsule도 상승 | CMC 충돌·바닥 판정·침투 해소·Root Motion 실행 |
| 서버는 안정적이고 클라이언트 Capsule만 크게 움직임 | proxy 이동과 서버 상태 복구의 차이 |
| Capsule은 안정적이고 Mesh/골반만 상승 | 포즈·루트 추출·Mesh 보정 |
| 무장애 W0에서도 큰 복귀 발생 | 기본 Montage/Root Motion 복제·슬롯·시간 상태부터 점검 |
| 벽 접촉 W2/W3에서만 보정 증가 | 충돌과 이동 복구가 결합된 현상 후보 |

현재 Enemy는 Simulated Proxy다. 이 문서의 Correction은 주로 proxy의 Root Motion fixup/SmoothCorrection/표시 보정을 뜻한다. 소유 플레이어의 ClientAdjustPosition RPC 횟수와 동일한 지표로 간주하지 않는다.

## 2. 최소 기록 파일

공통 키: RunId, TrialId, ScenarioRevision, ActorId, Generation, ReactionId, Role, WorldTime, WallTime. 위치 cm, 시간 s, 속도 cm/s를 사용한다. Generation은 같은 이름/ID의 Actor가 재생성된 문맥을 구분한다.

| 파일 | 필수 내용 |
|---|---|
| README.md | 작업 목적·명령·생성 시각/시간대·파일 설명·결과·보관 기준 |
| manifest.json | 빌드/엔진·맵·Montage/Section·L/T·재생/블렌드/충돌 설정·역할·네트워크·완료/저장 상태 |
| events.csv | 공격 요청/서버 접수/명중·미명중/피격 시작·중단·종료/벽 접촉/리셋 |
| server_samples.csv | 실제 이동 후 Capsule·속도·MovementMode·Montage track/재생 상태 |
| client_samples.csv | 프레임별 Capsule·기본 상대 offset을 구분한 Mesh·Montage track·frame time |
| corrections.csv | SmoothCorrection·root 상태 변경·proxy 실행 전후 차이와 각 이벤트 종류 |
| contacts.csv | 실제 벽 hit, 상대·normal·초기 침투 여부·진입/해제 |
| connections.csv | 연결 In/Out bytes·packets 누적 카운터. 가능하면 첫 기준선부터 수집 |
| video/ | 클라이언트 고정 카메라와 필요 시 서버 참고 영상 |
| summary.csv / report.md | 조건별 집계·발생 여부·제외 이유 |

첫 구현의 bytes/s는 기준선 기록이며 아직 동일 비용 개선 비교는 하지 않는다. Native Recorder 양식과 새 파일 양식을 섞어 기존 분석기가 지원한다고 가정하지 않는다. 최소 전용 수집/집계 또는 명시적 adapter를 작성한다.

## 3. 계측 위치

- 서버 샘플은 Enemy의 실제 이동 업데이트 이후 기록한다. 매 프레임의 Root Motion 요청과 실제 적용 변위를 가능하면 분리한다.
- 클라이언트 샘플은 CMC·Mesh smoothing 이후 기록한다. 샘플러의 tick prerequisite를 명시해 다음 프레임 상태와 혼합하지 않는다.
- 새 CMC의 SmoothCorrection override는 Super를 유지하고 Old/New Capsule, 적용 전후 Mesh를 기록한다. 이 수치가 실제 화면 순간 이동량과 같다고 가정하지 않는다.
- CMC의 SimulatedTick 전후와 GetRepRootMotion 상태 변경을 관찰해 일반 이동 수신과 Root Motion 복구를 구분한다. 설치된 UE 5.8의 `ACharacter::OnRep_RootMotion`/`SimulatedRootMotionPositionFixup`은 virtual이 아니므로 단순 override 계획을 세우지 않는다.
- 네트워크 수신 훅에서 관찰한 Root Motion 상태 변경 횟수는 패킷 수신 횟수가 아니다. 정확한 내부 fixup 분리가 필요하면 Networking Insights/별도 엔진 계측으로 검증한다.
- CMC HandleImpact만으로 모든 성공한 StepUp·초기 침투·지속 접촉이 관찰된다고 가정하지 않는다. 실제 hit + 관찰용 Capsule overlap/벽 거리 검사로 교차 확인하며 query 결과를 이동 제어에 사용하지 않는다.
- 클라이언트의 로컬 접촉을 근거로 새 서버 피격 사건을 만들지 않는다. 재시뮬레이션/복구에 따른 반복 접촉은 태그로 구분한다.

공식 자료: [FRepRootMotionMontage](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FRepRootMotionMontage), [CMC 네트워크 이동](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine).

## 4. 지표와 시간창

측정창은 준비·teleport가 끝난 안정화 시점부터 서버 Montage 종료 후 tail까지다. 공격 전 0.5초 이상을 기록하고, 피격 시작 이후/실제 벽 접촉 이후를 따로 집계한다.

| 지표 | 정의 |
|---|---|
| 실제 후방 변위 | 시작 방향 기준 Capsule의 최대 후방 이동, 서버/클라이언트 분리 |
| Capsule 상승 | Capsule bottom의 초기 안정 높이 대비 최대 상승·초과 지속 시간 |
| Mesh 상승 | 같은 기준의 Mesh 및 골반 변화. 애니메이션 자체 자세 변화와 함께 해석 |
| Capsule 관통 | 알려진 벽 collision과 Capsule의 blocking overlap 발생률·지속 시간 |
| 표시 관통 | 머리/몸통 proxy의 벽 침투와 영상. 정밀 mesh 관통량이라고 부르지 않음 |
| 보정 크기 | SmoothCorrection의 Old/New 차이 peak/p95/합계와 큰 사건 횟수 |
| 화면 튐 | Mesh 프레임 이동·속도 급변과 영상. 정상 피격 이동을 모두 보정으로 세지 않음 |
| 동기화 | server hit→client play 지연, Montage track 차이, 서버 궤적 대비 Capsule/Mesh 오차 |
| 안정화 | 서버 Montage 종료 이후 큰 위치 변동 없이 안정되는 시간; tail 내 미안정도 결과 |

긴 Montage가 원래 골반을 들어 올리면 Mesh Z만으로 잘못된 상승을 판정할 수 없다. W0의 같은 Montage 구간과 비교하고, 주 수직 지표는 Capsule bottom을 사용한다. 바닥·벽 형상은 조건 간 동일해야 한다.

초기 표시용 기준은 큰 보정 20cm, Capsule 추가 상승 5cm를 사용하되 확정된 성공/실패 판정은 아니다. 원시 연속값과 10/20/40cm 보정 민감도도 보관한다. 반복된 보정 이벤트는 frame/event 종류를 함께 기록해 한 복구를 중복 합산하지 않는다.

같은 PC의 서버·클라이언트는 UTC wall clock으로 정렬하고 server world time도 저장한다. 클라이언트의 추정 server time만으로 정밀 지연을 계산하지 않는다. 서버 위치는 동일 실행의 클라이언트 샘플 시각으로 보간해 비교한다.

## 5. 실행 순서와 반복 수

1. **연결 검증:** Standalone W0에서 피격 1회와 종료·리셋 3회. 뒤쪽 실제 변위가 L인지 확인.
2. **벽 기능 검증:** Standalone W2에서 실제 접촉과 기본 CMC 정지/slide 확인.
3. **복제 검증:** Dedicated Server + Client에서 N0 W0/W2 각 3회. 동일 ReactionId 재생이 한 번인지 확인.
4. **최소 측정:** W0/W1/W2/W3 × N0/N2 × 각 10회 = 네트워크 80 episodes.
5. **서버 동작 대조:** Standalone W0~W3 × 각 5회 = 20 episodes.

위 반복 수는 첫 문제 조사용이다. 유의성 검정이나 개선 우위를 확정하는 최종 연구 반복 수가 아니다. 무장애 L/T 측정은 별도 pilot으로 구분한다. W0에서 기본 복제가 잘못되면 네트워크 80회 수집 전에 수정한다.

N0/N2와 벽 거리 외에 Montage·재생 속도·Enemy 갱신 빈도·smoothing·fps·공격 타이밍은 고정한다. 네트워크에서 문제가 미미하면 추가로 10Hz/30Hz 빈도 대조를 할 수 있으나 별도 설정 군으로 기록하고 기본 결과를 덮어쓰지 않는다.

각 episode는 Ready 확인 → 기록 시작 → 공격 1회 → 서버 종료 → tail/저장 완료 순서다. 상태 실패나 watchdog으로 끝나면 이유를 기록한다. 관통/상승/미안정은 연구 결과이며 이를 무효 Trial로 제거하지 않는다.

## 6. 기록 품질과 저장 규칙

기술적 invalid 사유: 에셋/빌드 불일치, 서버 접속 실패, 잘못된 초기 겹침, 공격 미명중, Montage 재생 실패, 기록 저장 실패, 핵심 샘플 누락. 단, 공격 미명중 횟수도 별도로 보고해 조작/명중 경로의 품질을 확인한다.

벽에 막혀 이동량이 줄어든 것은 정상 결과다. 네트워크 지연으로 서버와 클라이언트의 Montage 종료 시각이 다른 것도 그대로 기록한다. 늦은 종료가 관찰창 밖이면 tail을 보완하고 기록 부족 원본도 보존한다.

PowerShell 실행/분석 전에 [NewSavedTask.ps1](../../Scripts/NewSavedTask.ps1)로 작업 폴더와 README를 만든다. 예:

```powershell
$task = ./Scripts/NewSavedTask.ps1 -TaskName 'HitWallBaseline' `
  -Description 'Player 정면 공격과 Enemy 긴 Root Motion 피격의 벽 충돌 기준선' `
  -Command '수동 Editor/독립 서버 실행; 실제 맵·인자는 run_meta.json에 기록' `
  -Artifacts @('run_meta.json: 실행 설정', 'Native/: 원본 CSV/manifest', 'video/: 화면 비교', 'report.md: 조건별 결과')
```

향후 새 실행기/분석기는 반환된 작업 폴더 아래에 결과를 쓰고 종료 시 README에 결과를 갱신한다. 이 명령 예시를 문서 작성 중 실행한 것은 아니다. 상세 규칙은 [Saved 결과물 관리](../Legacy/Workflow/Saved_결과물_관리.md)를 따른다.

## 7. 구현 완료 체크리스트

체크는 소스 존재 여부가 아니라 아래 조건을 **정량 실행 원본으로 확인했는지**를 뜻한다. 이미 구현된 공격·재생 기능도 Trial별 검증은 남아 있다. 단계별 완료 관문과 후속 연구 평가는 [07](07_단계별작업과평가.md)을 따른다.

- [ ] Player가 Enemy 앞에서 실제 공격하고 서버 sweep으로 명중을 확정한다.
- [ ] 같은 공격은 Enemy 피격을 한 번만 발생시킨다.
- [ ] 서버 Enemy와 Client Simulated Proxy가 고정된 긴 Montage를 한 번씩 재생한다.
- [ ] 무장애에서 Capsule이 의도한 뒤쪽 방향으로 실제 이동한다.
- [ ] 벽 가까운 조건에서 실제 Capsule 벽 접촉이 기록된다.
- [ ] 피격 Impulse·래그돌·Spline·커스텀 Predictor가 결과에 섞이지 않는다.
- [ ] Root Motion 재생·서버 이동·클라이언트 표시·보정이 기록으로 구분된다.
- [ ] 벽 거리별 관통/상승/큰 보정의 발생률과 크기가 집계된다. 0건도 정상 결과로 보고한다.
- [ ] Montage 종료·tail·저장·리셋이 정상 완료되고 늦은 이전 Trial 이벤트가 새 실행에 섞이지 않는다.
- [ ] 렌더링된 클라이언트 영상과 원본 CSV/설정/README가 함께 보관된다.

이 체크가 끝나면 [후속 개선 설계](06_후속개선_상세설계.md)의 안전 경로 검사·후보 선택·행동 계획 공유 중 실제 증상에 맞는 개선을 추가한다. 기준선에서 문제가 없으면 조건과 가설을 재검토하고 억지로 증상을 만들기 위해 기본 복제를 깨뜨리지 않는다. 이전 전체 설계는 [Legacy 연구계획](../Legacy/Research/RootMotion_피격_환경충돌_연구계획.md)에서 확인할 수 있다.
