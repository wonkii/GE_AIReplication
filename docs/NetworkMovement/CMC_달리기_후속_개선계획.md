# CMC 달리기 후속 개선 계획

2026-11-20 · GE_AIReplication · UE 5.8 · 다음 개발 단계 제안

**먼저 달리기 키를 누르거나 놓은 직후, 소유자와 서버가 같은 이동에 서로 다른 속도 상한을 적용하는지 확인한다.** 그 차이가 패킷 손실에서 반복되면 현재 MoveData를 채택할 근거가 생긴다. 다음 구현 후보는 달리기 키를 누른 채 웅크림을 해제할 때 양쪽이 같은 이동에서 달리기를 재개하는 정책이다. 두 질문은 별도 실험으로 다룬다.

## 출발점

기존 레벨 `/Game/JWJ/Lv_Jang`의 동일 출발점에서 `Fixed50 Straight`로 측정했다. 구성당 1회, 서버 검사와 소유자 이동이 각각 405개 대응했다. 각 방향에 50ms 지연을 추가했고 추가 손실은 0%였다. [기존 실험 명세](CMC_Baseline_컴포넌트비교_개발명세.md)

| 구성 | 같은 이동의 위치 오차 p95 | 소유자 보정 횟수 | 서버 최고 속도 | 원본 실행 ID |
|---|---:|---:|---:|---|
| Simple | 34.00027 cm | 34 | 350 cm/s | `A7CB822E` |
| SeparateRpc | 0.00468 cm | 0 | 650 cm/s | `683A7609` |
| MoveData | 0.00453 cm | 0 | 650 cm/s | `E083137A` |

Simple은 소유자만 달리기 속도에 도달하도록 구성한 미동기화 대조군이다. 서버가 걷기 속도 상한으로 이동을 재현하므로 이 군에서 오차와 보정이 예상된다. 실제 전달 방식 비교는 SeparateRpc와 MoveData 사이에서 한다. 이 실행에서는 두 방식 모두 보정이 0회였고 오차 p95 차이는 약 0.00015cm로 이동 위치의 직렬화 간격인 0.01cm보다 작았다. 원본은 `Saved/Tasks/*-SprintPIE-<구성>-<실행 ID>/summary.csv`와 같은 폴더의 역할별 CSV로 확인할 수 있다.

## 1. 첫 개발 작업은 전환 계측

현재 `TransitionP95Cm`은 단계 1·2의 입력 이벤트 후 500ms 안에 든 서버 검사 표본을 모은다. `Toggle`은 250ms마다 상태를 바꾸므로 한 표본이 여러 전환의 영향권에 든다. 또한 단계가 바뀌면 키 상태가 같아도 입력 이벤트가 남는다. 기존 수치를 유지하고 아래 지표를 별도 열로 추가한다. [입력 생성](../../Source/GE_AIReplication/Measurement/SprintTrialConsole.cpp) · [현재 집계](../../Source/GE_AIReplication/Measurement/SprintTrialReport.cpp)

- 소유자가 **실제 생성한 이동**에 기록한 달리기 의도와 서버가 그 이동의 시뮬레이션에 사용한 의도·속도 상한을 각각 기록한다. 이동 키는 실행 ID, 캐릭터, timestamp epoch, CMC move timestamp다. RPC 수신 순번은 서버 로컬 진단에만 쓴다. 계측용 필드를 네트워크에 추가하면 비교 대상의 패킷 자체가 달라진다. 기존 이동 기록 훅을 재사용할 수 있다. [관측용 CMC](../../Source/GE_AIReplication/Measurement/ObservedPlayerMovementComponent.cpp)
- 전환은 최초 예측에서 인접한 이동의 의도가 달라진 지점이다. 각 전환부터 **100ms 또는 다음 전환 직전 중 먼저 오는 시점**까지 고유하게 배정한다. 처음 100ms에도 표본이 없는 전환 수를 표시한다. 누름·해제별 표본 수, 속도 상한 불일치 수/대응 수, 서버 위치 오차 p95(cm)를 산출한다. 위치 오차는 기존과 같이 서버 검사 위치와 그 이동에서 소유자가 보고한 끝점 간 거리다.
- 저장 이동의 결합·패킷 손실로 대응하지 않은 표본은 별도로 센다. 전환이 통째로 누락된 횟수, 서버 검사 중 대응 비율, 실제 입력 전환 수, 실패 실행과 사유를 남긴다. 재생 시 같은 timestamp를 여러 번 볼 수 있으므로 최초 예측과 보정 후 재생을 구분한다. 보정 0회인 실행에서 재생 비용은 측정 불가로 표시한다.
- 완료 조건은 한 실행의 누름과 해제를 원본 CSV에서 추적해 요약을 다시 계산할 수 있고, 같은 서버 이동이 전환 두 개에 중복 배정되지 않는 것이다. 기존 세 실행은 종전 열로 다시 읽을 수 있어야 한다. 스키마 버전과 빌드 식별자, 전체 시작 좌표·방향, FPS·서버 tick 설정을 기록해 다른 조건이 같은 비교에 들어가는 것을 막는다.

## 2. 기존 단일 조건 PIE에서 전달 방식 비교

지터 100·200·300 ms와 손실률 0·10·20% 배치는 [9조건 개발 명세](CMC_Baseline_컴포넌트비교_개발명세.md)를 따른다. 단일 조건을 조사할 때는 기존 레벨의 평탄한 구간에서 두 클라이언트, Play As Client, Run Under One Process로 PIE를 시작한다. 같은 클라이언트의 `~` 콘솔에서 아래 두 줄을 **각 실험이 완료되고 원래 캐릭터로 돌아온 뒤 한 줄씩** 입력한다. 지금 사용할 수 있는 명령이다. 새 지표까지 수집하려면 1단계를 구현한 빌드로 반복한다.

```text
SprintTrial.Run SeparateRpc Loss Toggle 1
SprintTrial.Run MoveData Loss Toggle 1
```

| 순서 | 조건 | 확인할 질문 |
|---|---|---|
| 1 | `Fixed50 Straight` | 기존 기준선 재현. 두 동기화 구성에서 서버가 650cm/s에 도달하는가? |
| 2 | `Fixed50 Toggle` | 같은 고정 지연에서 빠른 키 전환만으로 적용 시점이 어긋나는가? |
| 3 | `Loss Toggle` | 각 방향 50ms를 유지하고 각각 2% 손실을 추가하면 전환 오차가 커지는가? 이번 후속 실험의 주 조건이다. |
| 4 | `Jitter Toggle` | 각 방향 50~100ms, 추가 손실 0%에서 같은 현상이 재현되는가? 평균 지연도 달라지므로 이 결과만으로 지터의 독립 효과를 추정할 수 없다. |

각 조건을 먼저 한 블록씩 수동으로 실행해 경로·원본·전환 대응을 확인한다. 본 측정은 주 조건과 대조 조건인 `Fixed50 Toggle`에서 각각 12블록씩 수행한다. 한 블록에 두 구성 각 1회를 실행하고 RPC 선행과 MoveData 선행 순서를 교차한다. 같은 시작점·방향과 버전으로 맞추고 블록 번호를 바꾼다. 블록 번호는 짝을 구분하는 값이며 동일한 패킷 손실 난수열을 재현하지 않는다. 8초짜리 한 실행에 설정 손실률이 그대로 나타난다고 가정할 수 없다. [기존 비교 스크립트](../../Scripts/CompareSprintTrials.ps1)

**판정 제안.** 주 지표는 블록별 `SeparateRpc 전환 100ms 위치 오차 p95 − MoveData 전환 100ms 위치 오차 p95`(cm)다. 누름·해제를 합친 값을 주 지표로 고정하고 각각의 값도 보고한다. 기존 비교 스크립트에 새 열을 연결해 **블록 단위** 차이의 중앙값과 bootstrap 95% 구간을 구한다. 파일럿과 본 측정은 따로 집계한다. 실용 기준의 초안은 **1cm**로 두고 본 측정 전에 확정한다. 신뢰구간 하한이 1cm를 넘고 속도 상한 불일치도 줄면 해당 조건에서 MoveData를 채택한다. 구간 전체가 ±1cm 안이면 두 방식이 실용 기준 안에 있었다고 기록한다. 경계를 걸치면 판단을 보류하고 반대 방향의 차이도 그대로 보고한다. 1cm는 프로젝트 판정 제안이며 플레이어 지각의 검증된 한계로 쓰지 않는다.

함께 볼 값은 전체 이동 p95·최댓값, 실제 소유자 보정 횟수/실행, 보정 후 위치 변화량, 재생 CPU 시간, 연결 전체 B/s, 실패율이다. 관찰자 창에서는 메시 오프셋과 갱신 간격을 확인한다. 관찰자 시각 품질과 소유자 위치 정확도는 각각 판정한다. 전환 대응이 한 구성에서 집중적으로 빠지거나 연결 비용·재생 비용이 반복적으로 커지면 그 조건의 채택은 보류하고 원본을 조사한다.

## 3. 첫 개선 후보는 웅크림 해제 시 달리기 재개

**재현할 상황**은 지상에서 웅크린 뒤 달리기 키를 누르고, 키를 계속 누른 채 일어나는 동작이다. 현재 별도 RPC의 `AcceptTransition`은 요청을 받을 당시 웅크린 상태이면 `bRequested`에 false를 저장한다. 일어난 후에도 키 상태가 그대로면 소유자가 다음 전환 RPC를 보내지 않는다. MoveData는 각 이동에 의도를 실어 보내고 서버에서 이동마다 조건을 평가한다. 이 코드 차이가 실제 서버 속도와 위치에 미치는 영향은 아직 측정 전이다. [달리기 정책과 SavedMove 구현](../../Source/GE_AIReplication/Measurement/SprintTrialCharacter.cpp)

1. **행동 계약을 고정한다.** 웅크리는 동안 CMC의 웅크림 속도를 사용한다. 키를 누른 채 실제로 일어설 수 있으면 첫 유효 지상 이동부터 달리기를 허용한다. 웅크린 중 키를 놓았다면 일어서도 걷는다. 천장 충돌로 일어서기가 거부되면 웅크림을 유지한다. 서버가 자신의 자세·이동 모드로 허용 여부를 판정한다.
2. **같은 입력을 받을 수 있는 PIE 코스를 추가한다.** 신규 코스 이름 제안은 `CrouchResume`이다. 모든 실험 캐릭터에서 CMC 웅크림을 활성화하고 같은 속도·입력 시간표를 사용한다. 먼저 머리 위가 열린 평지에서 재개와 해제를 확인한다. 유효성 검사는 서버가 650cm/s에 도달했는지에 의존하지 않고, 입력과 실제 자세 전환이 수행됐는지 확인한다. 재개 실패도 결과로 남겨야 한다.
3. **교체 가능한 달리기 정책을 구현한다.** 기존 `USprintTrialPolicy`에 키를 누르고 있는 의도와 그 이동에서 허용된 달리기를 구분한다. 소유자 최초 예측, 서버 재현, 보정 후 재생이 각 이동의 의도와 당시 자세로 같은 속도 결정 함수를 호출한다. RPC는 보유한 의도를 갱신하고, MoveData는 기존 `FLAG_Custom_0`를 사용한다. 기존 전환 경계의 이동 결합 방지와 `PrepMoveFor`의 의도 복원을 유지한다. 원격 관찰자는 서버가 복제한 이동을 표시한다.
4. **무엇이 개선을 만들었는지 구분한다.** 동일한 코스에서 전달 방식 두 종류(RPC·MoveData) × 속도 결정 정책 두 종류(현재·개선)를 비교한다. 각 전달 방식 안에서 정책만 바꾼 차이를 먼저 구한다. 실험 캐릭터에 정책을 선택하는 옵션을 추가하고 기존 한 줄 명령의 기본 동작을 보존한다.
5. **채택 조건을 확인한다.** 최초 예측·서버 재현에서 실제 기립 후 달리기 재개까지 걸린 이동 수, 의도·속도 불일치 수, 전환 위치 오차, 키를 놓은 뒤 잘못 달린 횟수를 기록한다. 재개와 해제가 계약대로 동작하고 같은 전달 방식의 현행 정책 대비 오류가 줄며 기존 `Straight`·`Toggle`의 오차와 보정에 회귀가 없는 후보를 게임 캐릭터 적용 대상으로 삼는다. 두 전달 방식이 모두 개선되면 공통 속도 결정 정책의 성과로 기록한다.

**개발 순서**는 전환 계측과 원본 재집계 → 기존 명령으로 손실·토글 비교 → 웅크림 재개 코스와 정책 교체 비교다. 첫 두 단계에서 두 방식의 차이가 계속 작더라도 세 번째 단계는 독립적으로 가치가 있다. 플레이어가 키를 계속 누르고 있는데 서버 캐릭터만 걷는 현상을 직접 판별하기 때문이다.
