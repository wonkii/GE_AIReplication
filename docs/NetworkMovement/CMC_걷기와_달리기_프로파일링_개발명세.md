# 기본 CMC 걷기와 달리기 전환 프로파일링 개발 명세

**대상은 UE 5.8 Development Editor의 전용 서버와 클라이언트 2개를 사용하는 단일 프로세스 PIE다.** 다음 구현에서 기존 시험기를 확장한다. 기본 걷기는 CMC 자체의 비용을 측정하는 기준군이다. SeparateRpc와 MoveData는 같은 달리기를 구현한 두 실험군이다. 여기서 SeparateRpc는 언리얼의 Reliable Server RPC를 뜻한다.

## 비교할 질문

| 질문 | 같은 입력으로 비교할 구간 | 판단에 쓸 값 |
|---|---|---|
| 달리기를 한 번도 요청하지 않았을 때, 달리기 지원 코드를 거치는 데 비용이 얼마나 드는가? | 세 방식 모두 시작 후 0–2초 직진 걷기 | 기본 걷기 대비 각 방식의 소유자 예측 시간, 서버 이동 처리 시간, 이동 RPC 비트 차이 |
| Shift를 반복해서 누르고 놓을 때 어느 방식에 비용이 발생하는가? | SeparateRpc와 MoveData의 2–4초 전환 구간 | 이동 RPC와 상태 RPC 각각의 비트·호출 수, 소유자 예측·보정 재생 시간, 서버 처리 시간, 같은 이동의 위치 오차와 보정 횟수 |
| 소유자 프레임이 길어졌을 때 이동 처리가 그중 얼마나 차지했는가? | 세 방식의 소유자 프레임과 해당 시점의 Game Thread 타임라인 | 프레임 간격, 같은 프레임 안의 예측·재생 시간, 단일 프로세스에서 함께 실행된 서버·관찰자·에디터 작업 |

네트워크 비용은 bits/s, CPU 비용은 호출당 시간과 초당 누적 시간으로 각각 판정한다. 보정 한 번이 빨라도 자주 재생하면 총비용이 커진다. 프레임 125 ms 초과는 입력 재현 실패를 나타내는 별도 결과다.

## 기존 명령어를 확장하는 근거

- `SprintTrialConsole.cpp`의 두 배치 명령은 같은 실행기로 들어간다. 소유자가 명령을 입력한 위치·카메라 방향, 서버와 원격 복제본 준비 확인, 아홉 가지 네트워크 조건, 입력 재생, 종료·취소 후 복구를 재사용할 수 있다. 현재 배치 명령 파서는 선택 인자 하나만 허용하며 `Spawn()`은 두 클래스 중 하나를 고른다.
- `SprintTrialCharacter.cpp`에서 두 실험군은 모두 `USprintStateMovement`와 `FSprintSavedMove`를 쓴다. Shift를 누르지 않아도 저장 이동 생성 및 달리기 정책 조회를 거친다. 기존 명령의 처음 2초는 각 실험군의 걷기 표본으로 쓸 수 있지만, 기본 CMC 표본은 따로 생성해야 한다.
- 현재 `server/network.csv`는 소유자·관찰자 연결별 양방향 바이트와 패킷 누계다. `SprintRpc`는 서버에서 상태 전환을 수락한 이벤트다. 어느 쪽도 송신 RPC별 전송 비트를 제공하지 않는다. `OwnerReplayP95Ms`는 보정 후 실제 재생 호출의 시간이며, 일반 예측 시간은 현재 기록하지 않는다.
- `SprintTrialReport.cpp`는 소유자가 달리기 상한에 도달했는지 검사한다. `CompareSprintTrials.ps1`은 기존 두 방식의 `ConditionHash, Block` 쌍을 비교한다. 기본 걷기에는 걷기 전용 완료 조건과 공통 구간 기준의 비교 키가 필요하다.

## 구현 후 사용할 명령

같은 PIE 세션의 같은 소유자 창에서 평탄하고 전방이 열린 곳에 정지한다. 아래 세 줄을 **한 배치가 끝날 때마다** 차례로 실행한다. 같은 블록에서는 캐릭터와 카메라를 직접 움직이지 않는다.

```text
SprintTrial.Run CmcWalk Matrix 1
SprintTrial.SeparateRpc 1 Profile
SprintTrial.MoveData 1 Profile
```

| 명령 형식 | 실행 계약 |
|---|---|
| `SprintTrial.Run CmcWalk Matrix [Block]` | 기존 단일 실행 명령에 걷기 전용 배치 분기를 추가한다. 프로파일링을 자동으로 켜고 지정한 블록에서 기본 걷기 9셀을 실행한다. |
| `SprintTrial.SeparateRpc [Block] Profile` | 같은 9셀에서 기존 전환 입력을 재생하고 Reliable `ServerRequestSprint`와 CMC 이동 RPC를 계측한다. |
| `SprintTrial.MoveData [Block] Profile` | 같은 9셀에서 동일 입력을 재생하고 `FLAG_Custom_0`가 포함되는 CMC 이동 RPC를 계측한다. |
| `SprintTrial.Close` | 현재 배치를 취소하고 소유권·시점·네트워크·시험기가 변경한 프레임 및 추적 설정을 복구한다. |

블록은 현행 범위 1–10000, 기본값 1이다. 두 기존 배치는 `Profile`만 붙여도 블록 1로 실행한다. 인자 없는 두 배치와 기존 `SprintTrial.Run <SeparateRpc|MoveData> ...`는 기존 시험과 출력 계약을 따른다. 걷기 분기는 내부적으로 같은 행렬 실행기를 호출한다. 명령 하나당 9셀, 한 비교 블록은 총 27셀이다. 반복 블록은 걷기→RPC→MoveData, RPC→MoveData→걷기, MoveData→걷기→RPC 순으로 시작 방식을 순환한다.

## 입력·환경 통제

- 모든 군은 매 셀마다 같은 발 위치·방향에서 새 시험 캐릭터를 생성한다. 캡슐, 걷기 상한 350 cm/s, 가속·감속, 복제 주기, 원본 메시·ABP, 루트 모션 처리, 소유자 카메라, 관찰자 시점과 계측 수준을 맞춘다. 시작 조건과 실제 사용한 이동 컴포넌트 클래스를 manifest에 기록한다. 현재 종료 코드가 고정 문자열로 쓰는 `MovementClass`도 실제 인스턴스에서 읽는다.
- 기본 걷기는 엔진 기본 클라이언트 예측 데이터와 `FSavedMove_Character`의 할당·결합·압축 플래그 경로를 사용한다. 공용 타이머를 위한 관측 전용 CMC 파생은 허용한다. 기본군은 달리기 정책 `Request/Apply`와 상태 전송을 건너뛴다. 서버와 소유자 모두 걷기 상한을 사용하고 관찰자는 동일하게 서버 복제를 받는다.
- 소유자 연결에만 현행 설정을 적용한다. 송신 기본 지연 50 ms에 지터 100/200/300 ms, 수신 고정 지연 50 ms, 양방향 각각 손실 0/10/20%의 9개 조합이다. 블록 번호는 짝을 맞추는 식별자다. 실제 손실 패턴과 패킷 수는 매 실행마다 달라질 수 있다.
- 준비 완료 후 기존 1초 워밍업을 거친다. 0–2초는 세 군 모두 전방 걷기, 2–4초는 두 실험군만 250 ms 간격으로 달리기와 걷기를 전환하며 기본군은 계속 걷는다. 4–6초는 전방 걷기, 6–8초는 정지, 이후 1초는 늦은 응답 수집이다. 4–6초에는 앞선 전환의 보정이 남을 수 있으므로 공통 걷기 비교에는 첫 2초만 사용한다.
- 프로파일 모드의 기본 목표는 60 FPS다. 세 배치에서 동일한 실제 시간 기반 프레임 상한을 적용하고 이전 값을 복구한다. 고정 시뮬레이션 델타로 히치를 가리지 않는다. 맵·빌드, 소유자 PIE 인스턴스, 하드웨어/RHI, 뷰포트 크기·품질, FPS 상한·VSync, 백그라운드 절전·포커스, 시간 배율, 추적 채널·상세도와 계측 버전을 기록한다. 환경 설정이 다른 실행은 자동으로 짝짓지 않는다. 실제 프레임 분포는 결과로 남긴다.
- `DeltaTime > .125f` 중단 기준을 유지한다. 실패 직전 프레임과 해당 프레임 번호, 실시간 간격·월드 DeltaTime·포커스·구간·실패 사유를 먼저 저장한다. 실패 셀은 비용 분위수에서 제외하고 시도 수와 실패율에 포함한다. 절전이나 이동 코드를 원인으로 지목하려면 해당 프레임 타임라인에서 확인한다.

## 네트워크 비트 측정

1. 프로파일 배치마다 CPU·프레임·북마크와 NetTrace를 함께 수집해 `.utrace`를 남긴다. 준비 단계에서 기록 가능 여부를 확인하고 세 군에 동일한 상세도를 적용한다. 프로세스에 이미 사용자가 시작한 추적이 있으면 소유권을 확인하고, 안전하게 사용할 수 없는 세션은 이유를 출력한 뒤 배치 시작 전에 종료한다.
2. 소유자 송신 방향에서 **시험 캐릭터의** `ServerMovePacked` 등 실제 사용된 이동 RPC와 `ServerRequestSprint`를 분리한다. PIE 인스턴스, 연결, 캐릭터 NetId, 패킷 시각과 셀 경계를 함께 사용한다. 서버 수신이나 관찰자 사본을 중복 집계하지 않는다. 패킹 경로와 실제 RPC 이름 목록을 원본에 남긴다.
3. 에디터용 후처리에서 UE 5.8 TraceServices의 NetProfiler 패킷 콘텐츠 이벤트를 읽는다. 함수 범위의 `EndPos - StartPos`를 한 번만 합산한다. 각 계열에 전송 비트 합계, 범위 수, bits/s, bits/호출을 기록한다. 이동 RPC 한 번에는 여러 저장 이동이 묶일 수 있다. 전체 연결의 송수신 B/s, 패킷 수는 별도 열로 유지한다. 이 함수 범위는 엔진의 압축 전 패킷 콘텐츠 기준이다. [Epic Networking Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-insights-in-unreal-engine)
4. 패킷 송신 시각을 기준으로 구간에 귀속한다. 입력 구간을 지나 송신된 전환이나 재전송도 확인할 수 있도록 후속 걷기·정지·배수 구간과 셀 전체 합계를 함께 낸다. 하나의 패킹된 RPC를 임의로 여러 구간에 나누지 않는다. Reliable 재전송이 `ResendBunch`로만 보이면 별도의 미귀속 재전송 비트로 남긴다. 서버 수락 횟수·소유자 논리 전환 횟수와 송신 콘텐츠 범위 수를 독립적으로 기록한다.
5. 추적이 정상이고 이동 RPC가 관측된 상태에서 기본 걷기·MoveData의 상태 RPC는 0회·0비트여야 한다. 추적 누락, 액터 매칭 실패, 함수 경계 식별 실패는 원인과 함께 `NA`로 남긴다. 소유자 연결 총량이나 플래그의 논리적 크기인 1비트로 추정하지 않는다.

## CPU 시간과 프레임 측정

| 지표 | 측정 경계와 단위 |
|---|---|
| 소유자 최초 예측 | 소유자 `ReplicateMoveToServer` 범위 안에서 수행한 `PerformMovement` 시간을 예측 물리 시간으로 측정한다. 바깥 호출의 포괄 시간도 별도 측정해 저장 이동 생성·결합·송신 준비가 포함된 비용을 비교한다. |
| 소유자 보정 재생 | 보정 수신, `ClientUpdatePositionAfterServerUpdate` 호출, 해당 호출에서 실제 재생한 저장 이동 수를 구분한다. 보정당 ms, 재생 이동당 ms, 구간당 총 ms와 ms/s를 낸다. 재생 없는 보정은 횟수에 남기고 재생당 시간은 빈값으로 둔다. |
| 서버 이동 처리 | Authority에서 실제 처리한 `MoveAutonomous`의 호출 수·시간을 측정한다. 별도 RPC 수락 핸들러 시간은 독립 항목으로 남긴다. |
| 프레임과 관찰자 | 소유자 월드 DeltaTime과 실제 프레임 간격의 p50/p95/max, 공통 엔진 프레임 번호, 포커스 변화를 기록한다. 관찰자 복제 수신 간격과 메시 오프셋은 기존 품질 지표를 활용한다. |

게임 스레드의 단조 시계로 호출 경과 시간을 측정한다. 원시 표본에 TrialId, 역할·프레임 번호, 구간, 시작·끝 시각, 가능한 경우 이동 epoch와 타임스탬프를 남긴다. CPU 구간 집계는 **실제로 실행한 시점**을 사용하고, 지연된 보정이 어느 이동에 해당하는지는 별도 키로 추적한다. 중첩된 부모·자식 스코프는 합산하지 않는다. 호출 수가 0일 때 누적 시간은 0이고 분위수는 비어 있다. 단일 프로세스의 에디터 프레임에는 세 월드의 작업이 들어가므로 역할별 스코프를 프레임에 겹쳐 본다. [Epic Timing Insights](https://dev.epicgames.com/documentation/en-us/unreal-engine/timing-insights-in-unreal-engine)

세 군이 같은 공용 관측 컴포넌트·시간 경계를 사용하도록 한다. 특히 현재 달리기용 `PostUpdate`는 예측 호출 안에서 이벤트 CSV를 포맷한다. 프로파일 경로는 공용 버퍼에 고정 크기 원시 표본을 적재하고 구간 종료 후 서식을 적용한다. 기본군에서도 같은 의미의 표본을 같은 빈도로 수집한다. 버퍼 누락 수와 계측 설정을 남긴다. 한 조건에서 추적 켬/끔의 프레임 분포를 대조해 관측 부담을 표시한다.

## 결과 파일과 비교 규칙

- 기존 `Saved/Tasks/<시각>-SprintMatrix-<방식>-<ID>/` 아래에 README를 먼저 생성한다. 실행 인자를 포함한 명령, 시각·시간대, 원본 열람 방법, 성공·실패와 보관 기준을 기록한다. 배치의 `batch.csv`와 추적 파일, 셀별 `manifest.json`, 역할별 CSV, `summary.csv` 구조를 재사용한다. CPU·프레임 표본과 RPC 범위 원본에는 요약 행에서 해당 셀·구간을 역추적할 키를 둔다.
- 셀별 `profile.csv`는 방식·블록·네트워크 조건·구간별 한 행이다. 구간 실제 경과 초, 프레임 수, 이동/상태 RPC 각각의 비트와 호출 수, 미귀속 비트, CPU 호출 수·총시간·p50·p95, 보정 수·재생 이동 수, 수집 상태·누락 수를 포함한다. 전환 위치 오차는 기존 `Transition100P95Cm`와 대응 표본 수를 병기한다. 기본 걷기에는 전환 지표를 적용하지 않는다.
- 배치 종료 후 trace를 닫고 해석한 뒤 프로파일 상태를 확정한다. 플레이 완료와 프로파일 자료 완전성을 각각 기록한다. 추출 실패 시 원본에서 후처리만 다시 실행할 수 있어야 한다. 캡처 중단·PIE 종료도 이미 기록된 실패 프레임과 원본을 보존한다. PowerShell 결과 폴더 생성에는 기존 `NewSavedTask.ps1`을 사용한다.
- `CompareSprintTrials.ps1`은 기존 보고서를 계속 읽고 프로파일 스키마가 있는 자료만 별도 비용 표로 집계한다. 공통 환경·입력 구간·네트워크·시작 자세·계측 버전의 키와 `Block`을 사용한다. 기존 해시에는 전체 시나리오명이 있으므로 걷기와 Toggle의 0–2초를 묶을 때는 별도 구간 비교 키를 만든다. 2–4초 키는 동일한 Toggle 실험군에만 부여한다.
- 같은 블록·조건에서 걷기는 `SeparateRpc − CmcWalk`, `MoveData − CmcWalk`, 전환은 `MoveData − SeparateRpc`의 짝차이를 낸다. 차이의 단위, 원값, 유효 블록 수, 시도·실패·누락 수와 표본 수를 함께 표시한다. 분모가 0이면 백분율은 비워 둔다. 한 블록은 기능 확인용이다. 경향은 반복 블록의 짝차이 중앙값과 분산 범위로 기술한다. 환경이 다른 블록, 중복 셀, 측정 불능 지표는 비교에서 구별한다.

## 다음 단계의 구현 순서와 완료 기준

1. **실행기와 기준군.** 명령 파서, 배치 선택, 캐릭터 생성, 입력 분기, 걷기 전용 보고 판정을 순서대로 연결한다. 개발 에디터 빌드 후 기본군의 소유자·서버 걷기 상한 350, 실제 전진, 관찰자 복제, 기본 저장 이동 사용, 상태 RPC 0을 확인한다. 두 달리기 군은 전환 입력과 기존 오차·보정 보고를 재현해야 한다.
2. **측정 경계 확인.** 0% 손실 셀에서 SeparateRpc의 각 전환과 상태 RPC를 대응시키고 두 실험군 모두 이동 RPC를 확인한다. Networking Insights에서 선택한 패킷의 함수별 비트와 추출기의 같은 범위 합계가 일치해야 한다. Timing Insights에서 동일 프레임의 최초 예측과 보정 재생을 구분하고 원시 표본으로 합계·분위수를 재생성한다.
3. **비교와 실패 검증.** 같은 위치에서 세 명령을 각각 한 번 실행해 9개 걷기 삼중 비교와 9개 전환 쌍이 만들어지는지 확인한다. 실행 조건 불일치·추적 누락은 비교 누락 사유로, 125 ms 초과는 프레임 근거가 남는 실패로 표시한다. 높은 손실 조건에서 지연 도착·재전송 분류를 확인하고 수동 취소·PIE 종료·정상 종료 후 원래 소유권, 카메라, 네트워크 및 프레임 설정을 확인한다. 기존 형식의 두 배치 결과로 이전 비교 보고서도 재생성한다.
