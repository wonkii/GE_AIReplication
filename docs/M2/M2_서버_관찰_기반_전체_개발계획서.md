# M2 전체 개발계획서 — 서버 Enemy 관찰과 Impulse 재현

> 작성: 2026-10-11 · 대상: GE_AIReplication / UE 5.8 · 상태: 구현 전 계획
>
> 선행: [M1 Editor 설정](../M1/M1_Editor_설정_가이드.md) · 단계 정의: [M2](M2_Impulse_재현.md) · 후속: [M3](../M3/M3_CMC_기준선_측정.md)

**구현 업데이트:** M2 C++ 기능을 추가했다. 실제 설정과 기능별 파일은 [Editor 설정 가이드](M2_Editor_설정_및_기능별_파일.md)를 따른다. 자동화 테스트는 사용자 요청으로 생략하며 에셋 배치·PIE 확인은 수동 절차로 남긴다. 이하 내용은 원래 설계 기준이다.

## 1. 목표와 개발 방향

M2에서는 서버 Enemy에 같은 Impulse를 반복 적용하고, **클라이언트 화면에서 보이는 Enemy와 서버의 실제 이동을 함께 관찰할 수 있는 환경**을 만든다. 서버의 Capsule 위치와 CMC Velocity를 기준 상태로 기록해, 화면에서 급변이 보이지 않는 원인이 서버 이동인지 복제·표시 지연인지 구분할 준비를 한다.

권장 구성은 다음 세 가지다.

1. **PIE Server Debug Drawing:** 클라이언트 화면에 서버의 실제 Capsule·Velocity를 도형으로 표시한다.
2. **Visual Logger:** 서버 궤적과 Impulse 사건을 기록하고 사건 전후를 타임라인에서 검토한다.
3. **서버 Recorder:** 이동 업데이트마다 수치를 저장해 M3에서 사용할 Ground Truth를 만든다.

M2의 완료는 재현·관찰·기록이다. Detector, 사건 Snapshot 전송, ForceNetUpdate 기반 개선, 클라이언트 예측은 각각 M4~M6의 범위로 유지한다. 클라이언트 관찰 화면의 차이를 곧바로 정량적인 네트워크 오차로 판정하지 않는다.

## 2. 현재 구현에서 활용할 부분

2026-10-11 소스 및 파일 목록 확인 기준이다. 에셋 내부 설정과 실제 PIE 동작은 이번 문서 작성에서 검증하지 않았다.

| 현재 구성 | 확인한 상태 | M2 활용 |
|---|---|---|
| `ASharpEnemyCharacter` | ACharacter/CMC, Actor·Movement 복제, ActorId·ExperimentContext 복제 | Impulse 대상과 서버 관찰 기준 Actor |
| `ASharpEnemyAIController` | 서버 Follower의 Prepare/Start/Suspend/Resume/Reset 호출 | 기존 제어 경로 유지 |
| `USharpSplineFollowerComponent` | 서버에서 CMC보다 먼저 입력 생성, `OnCharacterMovementUpdated`로 결과 관찰 | Recorder도 같은 이동 결과를 읽도록 확장 |
| `ASharpExperimentManager` | 수동 Trial 제어, Default Mode, 시작점 배치·TrialId 관리 | Volume 활성화와 기록 수명 관리 추가 |
| Enemy 진단 | 기본 1초 간격 로그와 TextRender | 빠른 Impulse 측정에는 별도 Recorder 필요 |
| `PrepareAtStart()` | 입력 소비, 즉시 정지, 누적 힘 제거, Teleport 후 Walking | 리셋 중 Volume이 발동하지 않도록 순서 제어 |
| 실험 에셋 | 실험 Map, Settings, Manager 파일 존재 | 기존 맵을 확장하되 Enemy/Path 연결은 Editor에서 확인 |

현재 `SharpMovement` 소스에는 Impulse Volume과 정밀 Recorder가 없다. M1은 NavMesh MoveTo가 아니라 Spline 기반 입력 추종이므로, Impulse 후 복귀에 영향을 주는 대상은 **SplineFollower와 CMC의 가속·마찰·제동 설정**이다.

## 3. Unreal 공식 관찰 기능 선택

### 3.1 우선 적용: Show Server Debug Drawing by Default

Epic의 PIE Multiplayer Options에는 **Show Server Debug Drawing by Default**, **Server Debug Drawing Tint Strength**, **Server Debug Drawing Color Tint**가 있다. 전용 서버의 디버그 렌더링을 PIE에서 표시하는 기능이다. [공식 PIE 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine)

요청한 작업 방식에 가장 가까운 기능이다. 클라이언트 Enemy를 계속 바라보면서 서버 상태를 색이 다른 도형으로 겹쳐 볼 수 있다. 다만 이 설정이 서버 Enemy Mesh를 하나 더 렌더링해 주는 것은 아니다. 프로젝트 코드에서 서버 위치에 관찰용 도형을 생성해야 한다.

개발 제안:

- 서버 이동 결과를 받은 뒤 실제 Capsule 위치·반높이·반지름으로 `DrawDebugCapsule`을 그린다.
- 같은 위치에서 `CMC->Velocity * ArrowTimeScale` 길이의 `DrawDebugDirectionalArrow`를 그린다. 기본 ArrowTimeScale은 0.2초로 둔다.
- 사건 위치에는 짧은 수명의 구와 Impulse 방향 화살표를 추가한다.
- 서버 도형은 주황색 계열, 선택적인 클라이언트 로컬 Capsule 도형은 청록색 계열로 구분한다. Tint 적용 후 실제 색을 확인한다.
- 이동 도형의 수명은 짧게 제한하고 Persistent Drawing을 사용하지 않는다. Editor Pause/Frame Skip으로 정지 관찰한다.
- `HasAuthority()`와 관찰 옵션을 모두 검사한다. Dedicated Server라는 이유만으로 서버 도형 생성 코드를 건너뛰지 않는다.

**첫 구현 게이트:** `Play as Client + Run Under One Process`에서 서버 Capsule 도형 하나가 클라이언트 화면에 나타나는지 먼저 확인한다. 공식 설정의 존재는 확인했지만, 프로젝트에서 선택한 DrawDebug 호출의 전달·수명·표시 월드는 PIE 실험으로 확인해야 한다. 별도 프로세스나 패키징 실행에 이 기능이 그대로 동작한다고 가정하지 않는다.

### 3.2 사건을 되짚기: Visual Logger

Visual Logger는 Actor 상태·텍스트·도형을 기록하고 타임라인에서 검토하는 공식 도구다. 서버 Enemy를 로그 소유자로 통일하고, 매 이동 업데이트의 위치·속도와 사건 ID를 남긴다. `UE_VLOG_LOCATION`, `UE_VLOG_ARROW`, `UE_VLOG` 및 `GrabDebugSnapshot` 확장을 사용한다. 기록 활성화가 필요하며, Snapshot에는 현재 상태를 넣고 개별 사건은 텍스트 항목으로 보존한다. [공식 Visual Logger 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/visual-logger-in-unreal-engine)

Volume·Controller·Enemy에 로그 소유자가 흩어지지 않게 `ASharpEnemyCharacter`를 중심으로 기록한다. 프로젝트의 Spline은 커스텀 이동이므로 실제 이동 위치를 직접 기록한다. 내장 AI 경로 표시만으로 이 궤적이 자동 기록된다고 가정하지 않는다.

서버와 Client가 같은 이름의 Actor를 갖는 PIE에서는 World/NetMode/ActorId를 함께 기록한다. M2의 Visual Logger는 기본적으로 서버만 사용한다. 수치 원본은 별도 CSV로 보존한다.

### 3.3 화면을 분리해서 볼 때: Listen Server 에디터 관찰

M1의 Listen Server + Client 2개 구성을 유지할 수 있다. 서버를 Selected Viewport에서 실행한 뒤 툴바 Eject로 에디터 카메라를 사용하고, 클라이언트들은 별도 창에서 Enemy를 관찰한다. Eject/Possess 지원 여부는 PIE 표시 방식에 따라 확인한다. 단축키는 설치 버전의 Editor 설정을 따른다. [공식 Play/Simulate 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/playing-and-simulating-in-unreal-engine)

Dedicated Server에는 로컬 플레이어와 게임 화면이 없다. 따라서 서버 관찰 창을 요구하는 방식은 Listen Server 확인용으로 쓰고, Dedicated Server 검증에는 디버그 도형과 기록을 사용한다. [공식 PIE 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine)

### 3.4 선택 확장: Gameplay Debugger

Gameplay Debugger는 네트워크 클라이언트에서도 서버 디버그 데이터를 표시할 수 있다. 커스텀 `FGameplayDebuggerCategory`에 ActorId·속도·MovementMode·Trial 상태를 추가할 수 있다. [공식 개요](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-the-gameplay-debugger-in-unreal-engine), [현행 Category API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/GameplayDebugger/EGameplayDebuggerCategoryState)

PIE 도형으로 관찰 요구를 충족하면 M2 필수 구현에서 제외한다. 별도 프로세스 클라이언트에서 실시간 서버 수치를 보고 싶을 때 추가한다. 이 경우 디버그 데이터 복제가 네트워크 부하를 추가하므로 M3 정량 측정에서는 비활성화한다. 개요 문서의 구형 예제 클래스보다 UE 5.8의 Category API와 설치 엔진 헤더를 기준으로 구현한다.

## 4. 전체 구조와 파일 책임

```text
Server
  ExperimentManager ── Trial 준비/시작/종료, Volume Arm, Recorder 수명
         │
  SplineFollower ── 입력 ──> Enemy CMC ──> 실제 이동 업데이트
         │                       ▲                 │
  ImpulseVolume ── AddImpulse ────┘                 ├─ Recorder → CSV
         └─ 사건 기록 예약 ─────────────────────────┤
                                                  ├─ Visual Logger
                                                  └─ Server Debug Drawing

Client 화면
  기본 복제 Enemy Mesh + 전달된 서버 디버그 도형
  기본 CMC Replicate Movement / Network Smoothing 유지
```

아래 이름은 개발 시 사용할 권장 계약이다. 경로는 저장소 루트 기준이며 새 파일은 아직 존재하지 않는다.

## 5. Impulse Volume 상세 설계

### 5.1 설정

| 설정 | 초기값/정책 | 의미 |
|---|---|---|
| `VolumeId` | 필수, 월드에서 유일 | 사건 출처 식별 |
| `TargetEnemy` / Manager | 지정된 Enemy 하나 | 플레이어와 다른 Pawn 제외 |
| Box Extent | Editor 조절 | QueryOnly, Pawn Overlap |
| `DirectionSpace` | `World` / `VolumeLocal` / `PathTangent` | 방향 해석 기준 |
| `ImpulseVector` | 기본 측면 Δv 300 cm/s | `bVelocityChange=true`에서 질량에 무관한 속도 변화 입력 |
| `bVelocityChange` | true | 최초 실험의 질량 변수 제거 |
| `TriggerPolicy` | 기본 `OncePerTrial` | 한 Trial에서 같은 Volume의 사건 1회 |
| `RearmDelay` | `OncePerEntry`에서만 사용 | 재진입 실험의 최소 사건 간격 |
| `FollowPolicy` | 기본 `Continue` | 입력 유지 / 일정 시간 입력 중단 |
| `InputSuspendSeconds` | 비교 실험에서 0.25초부터 | 임의의 출발값, 관찰 후 조정 |
| `bArmed` | 초기 false | 준비·리셋 중 발동 방지 |

초기 강도는 개발을 시작하기 위한 제안이며 실제 CMC 결과를 보장하는 수치가 아니다. VolumeLocal 방향은 회전만 반영하고 비균일 Scale로 세기를 바꾸지 않는다. PathTangent의 전방·측면 기준은 실제 호출 위치와 추종 방향에서 계산하고 **해석된 World Vector**를 기록한다.

### 5.2 충돌과 서버 권한

Box는 QueryOnly로 두고 Enemy Capsule과 양쪽 Generate Overlap Events 설정을 확인한다. Enemy Mesh 등 여러 Component의 Overlap을 하나의 진입으로 잘못 세지 않게 `OtherComp == Enemy->GetCapsuleComponent()`를 검사한다. 서버 이외 월드에서는 Volume 충돌을 비활성화하고, 핸들러에도 `HasAuthority()` 검사를 둔다.

Volume Actor는 `bReplicates=false`로 둔다. 레벨 배치 Actor가 클라이언트 월드에도 존재할 수 있으므로 복제 비활성화만으로 클라이언트 실행을 막았다고 판단하지 않는다. 클라이언트에서 AddImpulse를 재호출하거나 Mesh Physics에 힘을 가하지 않는다.

기본 `OncePerTrial`은 리셋 전까지 재발동하지 않는다. 선택적인 `OncePerEntry`는 Capsule의 EndOverlap 후 재진입과 Cooldown을 모두 요구한다. 같은 Volume 내부에서 여러 프레임 머물러도 Tick마다 힘을 적용하지 않는다. 준비 시 이미 Volume 안에 있으면 실패로 보고 시작 위치·Volume을 수정한다.

### 5.3 호출 순서

1. Authority, 대상 Capsule, 현재 Trial, Armed 상태, 중복 여부를 검증한다.
2. 재진입을 막을 발동 상태를 **먼저** 설정한다.
3. 서버 Recorder에서 `EventId`를 생성하고 호출 전 위치·속도·Mode와 World Impulse를 저장한다.
4. `CMC->AddImpulse(WorldImpulse, true)`를 정확히 한 번 호출한다.
5. 호출 완료 시각을 기록하고 사건을 `PendingObservation`으로 둔다.
6. 이후 완료된 이동 업데이트에서 실제 상태를 기록하고 사건의 관찰 결과를 연결한다.

AddImpulse는 틱의 누적 힘으로 처리되므로 호출 직후 Velocity를 적용 후 상태라고 저장하지 않는다. 여러 호출은 누적될 수 있으며 Movement Mode도 바뀔 수 있다. [공식 AddImpulse API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UCharacterMovementComponent/AddImpulse)

## 6. Ground Truth와 시간 계약

### 6.1 이동 샘플링 지점

Recorder는 서버 Enemy의 `OnCharacterMovementUpdated`에 연결한다. 기존 Follower가 이미 같은 델리게이트를 사용하므로 최초 M2 구현에 커스텀 CMC 교체는 필요하지 않다. BeginPlay에서 바인딩하고 EndPlay에서 해제한다.

CMC의 OnMovementUpdated는 이동 업데이트 끝에서 실행되며, scoped movement 처리가 끝난 뒤 관찰하려면 Character 쪽 이벤트에 연결하라는 공식 설명이 있다. [공식 OnMovementUpdated API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UCharacterMovementComponent/OnMovementUpdated)

Recorder는 CMC 위치·Velocity·Mode를 읽기만 한다. 같은 델리게이트의 구독자 호출 순서에 의존해 Follower 상태 전환을 제어하지 않는다. Follower가 Completed/Failed를 통지하더라도 마지막 이동 샘플을 저장한 뒤 기록을 닫도록 종료를 지연한다. 한 프레임에 이동 업데이트가 여러 번 있을 수 있으므로 Frame만으로 행을 식별하지 않는다.

### 6.2 사건 시각을 구분한다

| 시각/상태 | 정의 |
|---|---|
| `VolumeOverlapTime` | 서버가 대상 Capsule BeginOverlap을 처리한 시간 |
| `ImpulseCallTime` | 서버가 AddImpulse를 호출한 시간 |
| `FirstPostCallSampleTime` | 호출 뒤 처음 받은 완료 이동 샘플의 시간 |
| `ActualVelocityChangeTime` | 이후 샘플에서 속도 변화가 관찰된 최초 시간; 미관찰이면 null |
| `EventStatus` | Pending / Observed / NoObservableChange / Cancelled / Invalid |

월드 시간은 같은 프레임의 Overlap과 이동 콜백에서 같을 수 있다. 따라서 서버 `FrameNumber`, 단조 증가 `RecordOrdinal`, `SampleId`와 `DeltaSeconds`도 저장한다. 시각이 같다고 순서를 역추정하지 않는다.

중요한 구분: 첫 호출 후 샘플에는 Impulse뿐 아니라 가속·마찰·중력·충돌이 함께 반영된다. 특히 이동 중 Overlap이 발생하면 첫 콜백이 누적 Impulse를 소비하기 전일 수 있다. 따라서 `FirstPostCallSampleTime`을 Impulse의 정확한 내부 적용 시각으로 명명하지 않는다.

초기 구현은 사건 후 0.5초의 관찰 창과 속도 변화 허용치 1 cm/s를 제안값으로 둔다. 이동 전후 `OldVelocity`, `CurrentVelocity`, 호출 직전 Velocity를 모두 보존하고 변화량을 저장한다. 변화가 나타나지 않아도 행을 삭제하지 않고 NoObservableChange로 남긴다. 상향 사건의 Walking→Falling 전환은 별도 항목이다. 이 변화 판정은 M2의 사건 관찰 메타데이터이며 M4 Detector의 입력·정답 판정으로 재사용하지 않는다.

Impulse 소비 순간의 엄밀한 시각이 반드시 필요해지면 설치된 UE 5.8 CMC 구현을 확인하고, `ApplyAccumulatedForces` 전후를 기록하는 최소 커스텀 CMC를 별도 작업으로 추가한다. 이때도 Super 동작을 유지하며 다른 누적 힘과의 분리 가능성을 확인한다. M2의 기본 산출물은 **이동 업데이트 해상도의 관찰 시각**이다.

### 6.3 파일 계약

출력 제안 경로: `Saved/SharpMovement/<RunId>/Trial_<TrialId>/<ProcessId>_<WorldId>/`.

| 파일 | 필수 내용 |
|---|---|
| `manifest.json` | SchemaVersion, 엔진·빌드 식별, 실행 역할, 시나리오 설정, CMC/복제 설정, 관찰 옵션, 지연·손실 설정 |
| `server_samples.csv` | RunId, TrialId, ActorId, PathId/Revision, Frame, RecordOrdinal, SampleId, ServerWorldTime, DeltaSeconds, Position XYZ, OldVelocity XYZ, Velocity XYZ, MovementMode/CustomMode, FollowPolicy |
| `events.csv` | EventId, VolumeId, 호출 전 상태, World Impulse, bVelocityChange, 각 사건 시각, 연결 SampleId, 관찰 변화량, 사건 상태 |
| Visual Logger 저장 파일 | 동일 ActorId/EventId와 World 역할을 포함한 시각 기록 |

`EventId`는 Run 내 단조 증가값으로 두고 전체 키는 `RunId + TrialId + ActorId + EventId`로 한다. 공통 사건 번호는 M5 Snapshot SequenceId와 분리한다. 일반 이동 샘플은 사건 유무와 무관하게 저장한다. M4 Detector는 events.csv, Volume 참조, Pending 사건 정보를 읽지 않는다.

서버는 `GetWorld()->GetTimeSeconds()`를 권위 월드 시각으로 저장한다. M3에서 Client는 동기화된 GameState 서버 시각 추정값을 별도 필드로 기록하며, 정확한 패킷 수신·보정 시각은 후속 단계에서 추가한다. M2에서 서버·클라이언트 위치를 같은 화면에서 겹쳐 보이는 것만으로 시간 정렬이 완료된 것은 아니다.

매 이동 업데이트에서 샘플을 만들되 파일 I/O는 버퍼에 모아 일정 주기와 Trial 종료에 Flush한다. 종료·실패·Reset에서도 Flush하고, 디스크 오류와 버퍼 제한 초과는 결과에 남긴다. 설정 변경은 Trial 사이에서만 허용한다.

## 7. Manager와 SplineFollower 통합

### 7.1 Prepare/Start/Reset 수명

**Prepare:** 모든 Volume Disarm → 이전 기록 종료 → 사건·중복 상태 초기화 → 기존 PrepareAtStart → 시작점과 Volume 겹침 검사 → Recorder를 새 Trial에 연결 → Ready. Teleport 중 발생한 Overlap과 속도 초기화는 사건에서 제외한다.

**Start:** Ready 확인 → Recorder 시작 및 초기 샘플 저장 → Volume Arm → 기존 StartFollow. 실패하면 Disarm하고 실패 사유와 함께 기록을 닫는다.

**Reset:** 먼저 Disarm → 복귀 Timer 해제 → Pending 사건을 Cancelled로 저장 → 기록 Flush → 기존 Follower Reset 및 TrialId 증가 → 새 Prepare. 이전 Trial의 Timer가 새 Trial의 Enemy를 재개하면 안 된다.

**Completed/Failed:** 새 사건을 막고 마지막 이동 샘플을 보존한다. 필요하면 설정한 0.5초 후행 관찰 구간까지 기록한 뒤 종료한다. 자동 반복은 이 구간 종료 후에만 허용한다.

### 7.2 Impulse 이후 입력 정책

우선 `Continue`로 현재 Spline 추종을 유지한다. 이것이 실제 운영 조건에 가까운 주 실험이다. Follower가 즉시 경로로 돌아오는지, 강한 Impulse가 Projection/Blocked 검사를 실패시키는지도 기록한다. 해당 검사를 측정 중 몰래 비활성화하지 않는다.

비교용 `SuspendInput`은 신규 입력만 일정 시간 멈춘다. 기존 Controller/Follower Suspend·Resume을 활용하되 Manager의 Running↔Suspended 상태 전환과 일관되게 연결한다. 이미 입력이 누적되었다면 해당 사건 프레임의 남은 입력을 소비할지 정책으로 명시하고 기록한다. `StopMovementImmediately()`를 Impulse 뒤에 호출하지 않는다.

재개 Timer에는 TrialId와 대상 Enemy를 확인하는 조건을 두며 수동 Suspend, Reset, Failed, EndPlay 시 취소한다. Falling 중에는 기존 `AllowInputWhileFalling=false` 정책도 기록한다. Continue와 SuspendInput 결과를 같은 조건의 반복으로 섞지 않는다.

### 7.3 Dedicated Server의 시작 경로

현재 Details 버튼은 서버에서만 동작하므로, Client Details 버튼으로 화면 없는 서버를 조작할 수 없다.

M2에는 **기본 꺼짐인 서버 자동 시작 옵션**을 추가한다. 제안 설정은 `bAutoStartTrial`, `AutoStartDelaySeconds`, `bAutoRepeat`, `RepeatCount`다. 서버 BeginPlay 이후 대상·Settings 초기화가 끝나면 Prepare하고, 명시한 Warm-up 지연 후 Start한다. 각 반복은 후행 기록 종료 → Reset → Ready 확인 → Warm-up → Start를 따른다. 준비 실패 시 반복을 중단한다. 고정 지연은 클라이언트 연결 완료를 보장하지 않으므로 화면 관찰 전 Client가 실제 연결됐는지 확인한다.

수동 Client 시작 UI가 필요해지면 플레이어가 소유한 PlayerController의 서버 RPC로 Manager 명령을 전달한다. Enemy/Manager에 임의로 Client 소유권을 부여하지 않는다. 이는 선택 확장이며 최초 M2에는 자동 시작으로 Dedicated Server 검증 경로를 확보한다.

## 8. Editor 실행 절차

### 8.1 첫 단계: Listen Server에서 사건과 로그 검증

1. 기존 실험 맵의 Enemy/Path/Manager 연결과 ActorId/PathId를 확인한다.
2. 직선 경로 중간, 시작점 및 끝점 감속 구간에서 떨어진 위치에 Volume을 둔다. 첫 장면은 넓은 평면과 장애물 없는 경로로 만든다.
3. `Play as Listen Server`, Players 3, `Run Under One Process` 켜짐으로 실행한다.
4. 서버를 에디터 관찰 가능한 Viewport로 실행하고, 서버 월드의 Manager에서 Prepare/Start한다.
5. Client 창에서 Enemy를 계속 관찰한다. 서버 관찰은 서버 월드 도형과 Visual Logger를 사용한다.
6. 같은 EventId에 AddImpulse 호출 한 번과 전후 이동 샘플이 연결되는지 확인한다.

### 8.2 주 관찰 환경: Dedicated Server + Client 화면

1. Advanced Play Settings에서 `Play as Client`, Players 2, `Run Under One Process` 켜짐으로 시작한다.
2. `Show Server Debug Drawing by Default`를 켜고 Tint Color/Strength를 조절한다.
3. M2의 서버 Capsule·Velocity Drawing 옵션을 켠다. 필요하면 Client 로컬 Capsule도 별도 색으로 그린다.
4. 자동 시작 Warm-up을 충분히 주고 Client 카메라를 실험 영역에 고정한다. 카메라는 Enemy를 Possess하지 않는 로컬 관찰 카메라로 둔다.
5. 서버 도형과 Client Mesh를 동시에 보며 사건을 관찰한다. 도형 소유 역할과 ActorId는 로그로 검증한다.
6. Visual Logger 기록을 저장하고 서버 CSV와 함께 EventId로 찾아 검토한다.

카메라가 기존 플레이어로 충분하면 신규 카메라 시스템을 만들지 않는다. 연속 관찰이 어려운 경우 맵에 CameraActor를 배치하고 Client의 로컬 PlayerController에서 View Target을 설정하는 작은 확장을 추가한다.

### 8.3 별도 프로세스 검증

그다음 `Run Under One Process`를 끄고 같은 사건·서버 로그가 유지되는지 확인한다. PIE Drawing 전달 가능 여부는 별도로 확인하며 미지원이면 서버 CSV·Visual Logger 저장 기록으로 검증한다. 별도 실행 서버의 Visual Logger 파일 기록 활성화와 저장 API는 설치 UE 5.8 헤더에서 확인한 뒤 구현한다. CSV는 Visual Logger 지원 여부와 무관하게 남긴다.

패키징 Dedicated Server는 전용 Target·빌드 환경 준비가 추가로 필요할 수 있다. M2에서 PIE Dedicated 검증과 패키징 서버 검증을 구분해 결과를 기록한다.

## 9. 실험 시나리오와 반복 조건

초기 목표 속도는 M1의 300 cm/s를 유지한다. 아래 Δv는 `bVelocityChange=true`에서의 입력값이며 실제 결과는 로그로 확인한다.

| 시나리오 | 제안 입력 | 목적 |
|---|---|---|
| Control | Volume 비활성 | 정상 이동의 속도 변화 비교 |
| Side | 측면 150 / 300 / 600 cm/s | 옆으로 밀린 뒤 경로 복귀 |
| Forward | 전방 150 / 300 / 600 cm/s | 속도 증가와 CMC 재조정 |
| Backward | 후방 150 / 300 / 600 cm/s | 감속·정지·방향 반전 가능성 |
| Up | 상향 300 / 600 cm/s | Falling 진입과 착지 |
| SmoothTurn/Stop | Volume 없이 완만한 곡선 / 끝점 감속 | M4 오탐 평가를 위한 정상 샘플 |
| Input comparison | 같은 Side 설정에서 Continue / SuspendInput | 추종 입력의 영향 분리 |

구현 확인은 대표 Side 한 조건을 3회, 재현성 확인은 대표 Side/Backward/Up을 각각 10회 수행한다. 강도 전체 조합은 대표 조건이 통과한 뒤 늘린다. 반복 횟수는 통계적 충분성을 입증하는 기준이 아니라 초기 검증 규칙이다.

네트워크 에뮬레이션은 우선 끈다. 동일 설정 반복에서는 시작 Transform, PathRevision, CMC 수치, TargetSpeed, 입력 정책, 서버 Δt, 복제 빈도를 저장한다. 물리·프레임 타이밍으로 인해 완전히 같은 궤적을 요구하지 않고 사건 수·상태·전후 속도 범위를 비교한다. 지연·지터·손실과 오차 통계는 M3에서 추가한다.

## 10. 개발 순서와 통과 기준

| 순서 | 작업 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| M2-A | 서버 관찰 최소 구현 | Client 화면에서 지정 Enemy의 서버 Capsule 도형 확인 |
| M2-B | Volume + Event 계약 | 서버에만 AddImpulse 1회, 동일 Trial 중 중복 없음 |
| M2-C | Recorder | 호출 전/후 SampleId, 시간·순서·실제 Velocity 저장 |
| M2-D | Visual Logger + CSV | 동일 ActorId/EventId로 사건을 두 기록에서 찾음 |
| M2-E | Manager 수명·자동 시작 | Reset/실패/자동 반복에 Timer·Pending 사건 누수 없음 |
| M2-F | 강도·방향·입력 비교 | 대표 조건 반복과 정상 Control 로그 확보 |
| M2-G | Dedicated + 별도 프로세스 | 로컬 플레이어에 의존하지 않고 사건·기록이 유지됨 |

먼저 서버 Drawing 한 개를 확인하면 관찰 경로의 불확실성을 빠르게 줄일 수 있다. 이후 기능마다 같은 Side 사건을 사용하고, 강도 행렬은 기록 체계가 안정된 뒤 진행한다.

## 11. 필수 검증 체크리스트

- [ ] Client의 서버 도형과 Enemy Mesh가 동일 ActorId에 대응한다.
- [ ] Client에는 Impulse 적용 로그가 없고 서버에만 사건이 생성된다.
- [ ] Capsule과 Mesh가 함께 겹치더라도 AddImpulse는 한 번만 호출된다.
- [ ] OncePerTrial, 선택적 OncePerEntry의 차이가 명확하게 동작한다.
- [ ] Prepare/Reset Teleport에서는 사건이 생성되지 않는다.
- [ ] 호출 직후 Velocity를 PostVelocity로 오기록하지 않는다.
- [ ] 동일 시각의 행도 RecordOrdinal/SampleId로 순서를 구분한다.
- [ ] 적용 후 변화 미관찰, 충돌, Falling, Follower Failed가 결과에 남는다.
- [ ] Reset 시 이전 사건의 Timer와 Pending 기록이 새 Trial로 넘어오지 않는다.
- [ ] Trial 종료·실패·EndPlay에서 마지막 샘플과 버퍼를 Flush한다.
- [ ] 관찰 비활성 상태에서도 서버 CSV 사건 기록이 가능하다.
- [ ] Gameplay Debugger 등 추가 디버그 복제를 끈 상태로 M3에 인계한다.

C++ 변경 후 Editor 빌드를 수행하고 위 항목은 PIE 실제 실행으로 확인한다. 로직 단위 검증은 중복 발동·Trial 초기화·사건 순서처럼 실패 영향이 큰 부분에 한정한다. 화면 Drawing·Overlap·이동 시각 검증은 단위 테스트로 대체하지 않는다.

## 12. 완료 산출물과 M3 인계

완료 시 신규 Volume/Recorder 소스, Volume Blueprint, 갱신된 실험 맵, 서버 관찰 설정 가이드, 대표 조건의 Manifest·CSV·Visual Logger 기록을 남긴다. 확인한 실행 환경과 미확인 환경도 결과 문서에 구분한다.

M3에는 시간·SampleId가 있는 서버 궤적, 독립적인 사건 정답 로그, 입력 정책과 CMC 설정을 전달한다. M3가 Client Capsule/Mesh의 표시 시점·복제 수신·보정량을 추가하여 정량 비교한다. M4는 이동 샘플만 관찰하는 Detector를 만들고 M2 사건 로그는 사후 평가에만 사용한다.

**M2 최종 완료 조건:** 지정한 Client 화면에서 서버의 이동 도형을 관찰할 수 있고, 같은 설정으로 급변 전후 Velocity·Movement Mode를 반복 확인하며, 사건 시각의 해상도와 한계를 명시한 서버 기록을 저장할 수 있다.
