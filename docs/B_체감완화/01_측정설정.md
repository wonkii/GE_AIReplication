# 01. B(체감 완화) 측정 설정

기준일: 2026-11-18 KST. 브랜치 `YHJ-rubberband-mitigation`. **이 문서는 B 담당이 먼저 정한 기본값이다.** A·C도 같은 조건표·기록 형식을 쓰면 결과를 한 표에 놓을 수 있으니, 다르게 가야 하면 이 문서를 고쳐서 맞춘다.

## 1. 범위

- 대상: **Client A 화면에 보이는 Client B 캐릭터**(Simulated Proxy). 자기 캐릭터 교정(Autonomous Proxy)은 A(예방)와 겹치므로 B 4단계(선택)로 미룬다.
- 목표: 지연·지터·손실 때문에 생기는 위치 보정이 화면에서 덜 튀고 덜 끌려가 보이게 한다. **위치 오차 자체를 줄이는 것은 A의 몫이고, B는 남은 오차가 보이는 방식을 다룬다.** 대신 화면 위치와 서버 위치의 차이가 정해 둔 상한을 넘지 않아야 한다.

## 2. 추가한 코드

| 파일 | 역할 |
|---|---|
| `Source/GE_AIReplication/Rubberband/RubberbandCharacter` | 템플릿 캐릭터 + 기록용 CMC + 자동 입력. BP 자식으로 사용 |
| `.../RubberbandMovementComponent` | 엔진 동작 그대로, Simulated Proxy 보정(`SmoothCorrection`)을 기록기에 알림. 2단계 적응형 스무딩도 여기에 넣는다 |
| `.../RubberbandInputScriptComponent` | Client B의 고정 입력 패턴 재생(`rb.Script.Start`) |
| `.../RubberbandRecordingSubsystem` | 월드마다 하나. 서버·클라 위치와 보정, 스무딩 설정, 실제 적용된 에뮬레이션 값을 CSV/JSON으로 기록. 스무딩 방식 전환 CVar 제공 |
| `Scripts/Analysis/rubberband_metrics.py` | 조건별 지표 계산 |

공용 변경은 하나다. `AGE_AIReplicationCharacter` 생성자가 `FObjectInitializer`를 받도록 바꿨다(기본 인자라 기존 BP·코드 동작은 같다). 자식 클래스가 CMC 클래스를 바꾸려면 필요하다.

## 3. 에디터 준비 (1회)

1. `BP_ThirdPersonCharacter`를 복제해 `BP_RubberbandCharacter`로 만들고, Class Settings → Parent Class를 `RubberbandCharacter`로 바꾼다.
2. 테스트 맵(평지, 예: `/Game/YHJ/Lv_Rubberband`)을 만들고 World Settings → GameMode Override에서 Default Pawn을 `BP_RubberbandCharacter`로 지정한다. PlayerStart는 서로 겹치지 않게 2개 이상 둔다.
3. 장애물은 처음에는 두지 않는다. 평지에서 러버밴딩이 나오는지부터 본다.

## 4. 네트워크 조건

**지연은 Client A(보는 쪽)의 받는 쪽에만 건다.** B 캐릭터 움직임은 "Client B → 서버 → Client A" 경로로 보이는데, 지연을 한 곳에 두면 해석이 깔끔하다.

| 이름 | `PktIncomingLagMin` / `Max` (ms) | `PktIncomingLoss` (%) | 보는 것 |
|---|---|---|---|
| N0 | 0 / 0 | 0 | 기준 |
| L100 | 100 / 100 | 0 | 고정 지연 |
| L200 | 200 / 200 | 0 | 고정 지연 |
| L300 | 300 / 300 | 0 | 고정 지연 |
| J50-150 | 50 / 150 | 0 | 지터 |
| J100-300 | 100 / 300 | 0 | 지터 |
| L200-P3 | 200 / 200 | 3 | 손실 |

- Min ≠ Max이면 패킷마다 그 사이에서 지연이 정해진다. 그래서 평균 지연과 지터를 분리하려고 L과 J를 따로 둔다.
- 실제로 적용된 값은 각 프로세스의 `*_meta.json`의 `PacketSimulation`에 남는다. 측정 후 반드시 확인한다.

## 5. 스무딩 조건 (1단계 기준선)

| 이름 | 설정 |
|---|---|
| Disabled | `rb.Smooth.Mode 0` (즉시 보정) |
| Linear | `rb.Smooth.Mode 1` |
| Exponential | `rb.Smooth.Mode 2` (프로젝트 기본. `AGE_AIReplicationCharacter::BeginPlay`가 0.06s로 바꿔 둠, 엔진 기본은 0.1s) |

`rb.Smooth.LocationTime <초>`로 스무딩 시간도 바꿀 수 있다(CMC가 캐시한 값까지 바꾼다. 기록되는 `SmoothLocationTime`은 실제 사용 값). 같은 BeginPlay에서 플레이어 NetUpdateFrequency도 60Hz(최소 30Hz)로 고정돼 있다. 보정 거리가 `NetworkNoSmoothUpdateDistance`(기본 384cm)를 넘으면 엔진이 스무딩 없이 순간 이동시킨다. 이는 `corrections.csv`의 `NoSmooth` 열로 기록된다.

## 6. Client B 이동 패턴

Client B 창에서 `rb.Script.Start [반복 수]`(기본 5). 입력은 `AddMovementInput`으로 넣으므로 실제 플레이어 경로(클라 예측 → 서버 → 다른 클라)를 탄다. 방향은 월드 기준(Yaw 0 = +X).

| 순서 | 단계 | 방향(Yaw) | 시간(s) | 의도 |
|---|---|---|---|---|
| 1 | Forward | 0 | 2.0 | 가속 |
| 2 | Stop | 입력 없음 | 1.0 | 급정지 |
| 3 | TurnRight | 90 | 1.5 | 직각 전환 |
| 4 | Reverse | 270 | 1.5 | 180° 반전 |
| 5 | Stop | 입력 없음 | 0.5 | 급정지 |
| 6~11 | Zig/Zag ×3 | 45 / 315 | 0.4씩 | 빠른 좌우 전환 |
| 12 | JumpForward | 0 + 점프 | 1.2 | 공중 이동 |
| 13 | Stop | 입력 없음 | 1.0 | 착지 후 정지 |
| 14 | ReturnHome | 시작점 방향 | 최대 8.0 | 반경 60cm 도착 시 종료(위치가 누적해서 밀리지 않게) |
| 15 | Rest | 입력 없음 | 1.0 | 다음 반복 전 정지 |

한 바퀴 약 15~20초. 대시는 넣지 않았다. 속도를 클라에서만 바꾸면 서버와 어긋나 자기 캐릭터 교정(A 영역)이 생기기 때문이다. 필요하면 CMC 저장 이동 플래그로 따로 구현한다. 단계 경계는 `client_B_script.csv`에 남아서 분석 때 구간을 나눌 수 있다.

## 7. 실행

### 7.1 PIE (빠른 확인)

1. Play 설정: Net Mode = Play As Client, Number of Players = 2.
2. Editor Preferences → Level Editor → Play → Multiplayer Options → Network Emulation: 켜고, Emulation Target = Clients Only, Incoming 지연·손실을 조건표대로 둔다. PIE에서는 B에도 같은 받는 쪽 지연이 걸리지만, 서버가 받는 B의 이동은 그대로라 A가 보는 B 움직임 측정에는 영향이 없다.
3. 콘솔(`~`) 하나에서 다음을 입력한다. CVar는 프로세스 전체에 적용된다.
   `rb.RunId Exp01` → `rb.Condition L200` → `rb.Smooth.Mode 2` → `rb.Record 1`
4. Client B 창에서 `rb.Script.Start 5`. 끝나면 `rb.Record 0`.

### 7.1-1 한 줄 실행: `rb.Run`

7.1의 3~4번을 한 번에 한다. **움직일 캐릭터(B)의 창**에서 입력한다.

```
rb.Run <Condition> [Loops=5] [SmoothMode] [SmoothTime] [RunId=자동]
예) rb.Run N0 1 2 0.06        // 기준선: Exponential 0.06s
    rb.Run L200 5 0           // 즉시 보정
    rb.Run J100-300 5 1 0.1   // Linear 0.1s
```

라벨·스무딩 CVar를 설정하고 `rb.Record 1` → 0.5초 뒤 스크립트 시작 → 마지막 반복 1초 뒤 `rb.Record 0`. RunId를 생략하면 `월일-시분초_Dis|Lin|Exp`로 자동 생성되어 폴더가 겹치지 않는다. 스무딩 덮어쓰기는 캐릭터에 남으므로 **실험에서는 SmoothMode·SmoothTime을 항상 적는다**(-1은 "직전 값 유지"라 재현이 안 된다). 네트워크 에뮬레이션은 명령으로 바뀌지 않으니 조건을 바꿀 때 PIE 설정(또는 실행 인자)을 먼저 바꾼다.

### 7.2 별도 프로세스 (정식 측정)

같은 PC에서 서버 1 + 클라 2를 띄운다. (`$UE` = UnrealEditor.exe, `$P` = .uproject, 맵 경로는 실제 맵으로)

```powershell
& $UE $P /Game/YHJ/Lv_Rubberband -server -game -log -port=7777 `
  -ExecCmds="rb.RunId Exp01, rb.Condition L200, rb.Record 1"
& $UE $P 127.0.0.1:7777 -game -log -windowed -ResX=960 -ResY=540 -SharpClientId=A `
  -PktIncomingLagMin=200 -PktIncomingLagMax=200 -PktIncomingLoss=0 `
  -ExecCmds="rb.RunId Exp01, rb.Condition L200, rb.Smooth.Mode 2, rb.Record 1"
& $UE $P 127.0.0.1:7777 -game -log -windowed -ResX=960 -ResY=540 -SharpClientId=B `
  -ExecCmds="rb.RunId Exp01, rb.Condition L200, rb.Record 1"
```

B 창에서 `rb.Script.Start 5` → 끝나면 세 창 모두 `rb.Record 0` 또는 종료(종료 시 자동으로 마감 기록).

### 7.3 규칙

- **CVar는 에디터를 끌 때까지 남는다.** PIE를 다시 켜면 `rb.Record 1`이 그대로라 시작하자마자 기록을 시도한다. PIE마다 `rb.RunId`를 새로 정하거나, 끝낼 때 `rb.Record 0`을 친다.
- **RunId·Condition 조합은 한 번만 쓴다.** 같은 폴더에 같은 파일이 있으면 기록기가 섞지 않고 멈춘다(로그 `Recording already exists`). 스무딩 방식별로 RunId를 나눈다(예: `Dis01`, `Lin01`, `Exp01`).
- 서버·클라는 반드시 같은 PC에서 돌린다. `HostTime`(`FPlatformTime::Seconds`)이 프로세스 간에 같은 시계라서 정렬에 쓴다.
- Listen Server 호스트 화면은 원격 캐릭터 스무딩 설정이 다르므로(`ListenServerNetworkSimulatedSmooth*`) 보는 쪽(A)으로 쓰지 않는다.

## 8. 기록 파일

`Saved/Experiments/Rubberband/<RunId>/<Condition>/` (Git 제외. README가 먼저 생성됨)

| 파일 | 내용 |
|---|---|
| `server_samples.csv` | 서버의 모든 플레이어 캐릭터 위치·속도 (`PlayerId`로 구분) |
| `client_<Id>_samples.csv` | 그 클라 화면의 캐릭터: `Capsule*`(캡슐), `Visual*`(메시 기준 화면 위치), 스무딩 방식·시간, 누적 보정 수·마지막 보정 거리. `NetRole`=Simulated가 남의 캐릭터 |
| `client_<Id>_corrections.csv` | 받은 보정마다: 보정 전·후 위치, 거리, 속도, 서버 상태 시각, 스무딩 설정, `NoSmooth` |
| `client_B_script.csv` | 자동 입력 단계 시작·종료 시각 (PIE에서는 클라 ID가 `PIE<n>`) |
| `*_meta.json` | 역할, 실제 적용된 패킷 시뮬레이션 값, 스무딩 덮어쓰기 값, 종료 사유(`Outcome`) |

공통 열: `RunId, Condition, Role, ClientId, PlayerId, NetRole, HostTime, ServerTime, Frame, FrameMs`. 기존 Recorder와 이름을 맞췄다(`ServerTime`은 클라에서는 추정 서버 시각).

## 9. 분석

```powershell
python Scripts/Analysis/rubberband_metrics.py Saved/Experiments/Rubberband/Exp01 Saved/Experiments/Rubberband/Dis01 ...
```

출력은 `Saved/Tasks/<시각>-rubberband-metrics-<id>/`(README 포함): `summary.csv`, `shift_curve.csv`, `report.md`.

| 지표 | 뜻 | B에서의 방향 |
|---|---|---|
| GapMean/P95/Max | 같은 시각의 화면 위치 − 서버 위치 | 상한 안에 있어야 함(반대 지표) |
| BestShiftSec, GapAfterShift | 지연만큼 당겨 비교했을 때의 추정 지연과 남는 차이 | 지연 항 분리용 |
| PopCount, PopPerMin | 한 프레임 화면 이동이 (지연 보정한) 서버 이동과 8cm 넘게 다른 횟수 = 튐 | ↓ |
| SpeedSpikes | 화면 속도가 750cm/s를 넘은 프레임(최대 500cm/s 캐릭터) | ↓ |
| AccelP95, JerkP95 | 화면 움직임의 부드러움 | ↓ |
| Corrections, CorrDist*, NoSmooth | 받은 보정의 수·크기·순간 이동 수 | 원인 설명용 |
| SettleMean/P95 | 보정 후 화면이 캡슐을 따라잡는 시간 = 끌려가는 시간 | 짧을수록 반응적, 너무 짧으면 튐 |

임계값은 `--pop-cm`, `--max-speed`, `--settle-cm`로 바꾼다.

## 10. 1단계 측정 순서

1. 평지 + N0 + Exponential로 한 번 돌려 파일·지표가 정상인지 본다.
2. 조건 7개 × 스무딩 3개 = 21회(각 5바퀴, 약 1.5분)를 측정한다.
3. 기본 스무딩이 가장 부자연스러운 조건(튐/분, 수렴 시간, 순간 이동)을 찾아 B의 구체적 문제 정의로 쓴다. 같은 장면의 화면 녹화를 함께 남긴다.

## 11. 검증 상태

- Python 분석 스크립트: 합성 데이터로 동작 확인(지연 0.1/0.2s 추정, 스무딩에 따른 튐 감소 확인).
- C++: **아직 빌드하지 않았다**(작성 환경에 UE 없음). 첫 빌드와 PIE 2인 실행으로 확인한 결과를 여기에 적는다.
