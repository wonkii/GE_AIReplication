# 02. 적응형 스무딩 설계 (B 2단계)

기준일: 2026-11-23 KST. 입력 데이터: 1차 배치 `B1123-2226`([01 문서 12절](01_측정설정.md#12-1차-결과-b1123-2226-pie-단일-프로세스-7조건--3방식--3바퀴)).

## 1. 풀 문제

**지연이 들쭉날쭉한(지터) 네트워크에서, 언리얼 기본 Exponential 스무딩(0.06s)으로도 원격 캐릭터가 1분에 190~320번 튀고, 보정 후 0.28~0.38초 끌려간다.** 고정 지연(100~300ms)과 손실 3%에서는 같은 설정으로 튐이 0~3회/분이다. 즉 기본 스무딩은 "늦음"은 감추지만 "도착 간격의 흔들림"은 감추지 못한다.

## 2. 원인 (측정으로 확인)

같은 배치의 Exponential 판, 보는 클라(A) 기준.

| 조건 | 도착 간격 p50 / p95 | 같은 프레임에 몰려 도착 | 80ms 넘게 끊긴 뒤 보정 크기 | 평소 보정 크기 | 튐 중 보정 직후 0.1s 이내 |
|---|---|---|---|---|---|
| L200 | 28 / 43ms | 0.1% | (11회) 0.5cm | 2.7cm | 100% (2회) |
| J50-150 | 27 / 84ms | 27% | (98회) 24.7cm | 10.2cm | 100% (169회) |
| J100-300 | 14 / 106ms | 44% | (187회) 31.4cm | 11.8cm | 100% (282회) |

흐름은 다음과 같다.

1. 지터가 있으면 업데이트가 **몰려 오고(한 프레임에 여러 개) 끊긴다(80~100ms 이상)**.
2. 끊긴 동안 클라는 원격 캐릭터를 마지막 속도로 **외삽**한다. 그사이 서버의 캐릭터가 멈추거나 방향을 바꾸면 외삽이 틀어진다.
3. 다음 업데이트가 오면 캡슐은 서버 위치로 바로 옮겨지고, 메시는 그 차이(25~31cm)를 0.06s 시간 상수로 따라잡는다. **0.06s에 30cm를 따라잡으면 화면 속도는 순간적으로 수백~1000cm/s 이상이 된다 → 튐.**
4. 고정 지연에서는 간격이 일정해 외삽 오차가 작고(3cm), 같은 0.06s 따라잡기로도 튀지 않는다.

따라서 B가 바꿀 것은 **보정을 화면에 펼치는 방식**이다. 서버·캡슐 위치(충돌·판정)는 건드리지 않는다. 메시 오프셋만 바꾸므로 A(예방)와 겹치지 않는다.

## 3. 방법

엔진 Exponential 스무딩 위에 세 가지를 얹는다. 지터가 없으면 기본과 똑같이 동작하도록 만든다(고정 지연·N0에서 손해가 없어야 한다).

### M1. 지터 추정기

- 보정을 받을 때마다 수신 시각 `R`(클라 시계)과 그 상태의 서버 시각 `S`(`GetReplicatedServerLastTransformUpdateTimeStamp`)를 쓴다.
- RTP(RFC 3550 6.4.1)의 도착 간격 지터를 그대로 쓴다.
  `D = (R_i − R_{i−1}) − (S_i − S_{i−1})`, `J ← J + (|D| − J) / 16`
  두 시계의 차이는 빼기에서 사라지므로 시계를 맞출 필요가 없다.
- 함께 기록: 직전 수신 이후 간격 `Gap`, 같은 프레임 묶음 수.
- 전제: 서버 시각이 복제되어야 한다. 1차 배치에서는 0이었고, `bNetworkAlwaysReplicateTransformUpdateTimestamp = true`로 고쳤다. 안 되면 `Gap`의 EWMA 편차로 대신한다.

### M2. 지터 적응 스무딩 시간

- `T = clamp(T0 + k·J, T0, Tmax)`, 기본 `T0 = 0.06s`(현재 프로젝트 값), `k = 1.0`, `Tmax = 0.25s`.
- 지터가 0이면 T = T0이라 지금과 같다. 지터가 커지면 따라잡는 시간을 늘려 화면 속도를 낮춘다.
- 적용 위치: `SmoothCorrection`에서 `Super` 호출 전에 `ClientData->SmoothNetUpdateTime = T`.

### M3. 보정 속도 제한

- 매 프레임 메시 오프셋이 줄어드는 양을 `Vc · dt`로 제한한다. 기본 `Vc = 300cm/s`. 즉 화면은 캡슐보다 최대 300cm/s 빠르게만 따라잡는다.
- 안전장치: 오프셋이 `Gmax`(기본 50cm)를 넘으면 제한을 풀어 Exponential 그대로 따라잡는다. 화면이 서버에서 너무 멀어지지 않게 한다.
- M2가 "얼마나 천천히"를 정하면, M3은 "아무리 커도 이 속도 이상은 아니다"를 보장한다.
- 적용 위치: `SmoothClientPosition_Interpolate` 뒤에서 오프셋 변화량을 자른다. 이 함수가 override 불가능하면 `SmoothClientPosition`을 override해서 앞뒤 오프셋을 비교한다.

### M4. (시간 남으면) 적응형 보간 지연

외삽 대신, 받은 상태들을 서버 시각으로 버퍼에 쌓고 `현재 − D` 시점을 보간해서 그린다(Valve의 `cl_interp` 방식). `D`를 M1의 지터(예: `J`의 p95)에 맞춰 자동으로 정한다. 외삽 오차 자체가 없어지는 가장 근본적인 방법이지만 지연이 `D`만큼 늘고 구현량이 크다. M1~M3 결과를 보고 결정한다.

## 5. 실험

| 이름 | 설정 | 왜 |
|---|---|---|
| Dis | 즉시 보정 | 하한 기준 |
| Exp | Exponential 0.06s | 현재 기준선 |
| Lin | Linear 0.06s (타임스탬프 고친 뒤 재측정) | 엔진 다른 모드 |
| Exp-0.15 / Exp-0.25 | 스무딩 시간만 고정으로 늘림 | **"그냥 길게 하면 되지 않나"에 대한 답.** 지터에선 좋아져도 고정 지연·N0에서 늘 늦어진다면 적응형의 이유가 된다 |
| Ada-T | M1+M2 | 시간 적응만의 효과 |
| Ada-R | M3만 | 속도 제한만의 효과 |
| Ada | M1+M2+M3 | 제안 방법 |

조건 7개 × 위 8개 × 3바퀴 = 56판, `rb.Batch` 약 55분. 같은 장면 비교 영상은 J100-300에서 Exp / Exp-0.25 / Ada 세 개를 녹화한다.

## 6. 판정 기준

- **좋아져야 할 것 (지터 조건)**: `SpikePerMin` Exp 대비 50% 이상 감소, `JerkP95`·`SettleMean`도 함께 감소.
- **나빠지면 안 되는 것**
  - 지터 없는 조건(N0, L100~L300, L200-P3): 모든 지표가 Exp 대비 ±10% 안.
  - 모든 조건: `GapAfterShift`(지연 뺀 화면-서버 차이) 증가 5cm 이내, 화면-서버 차이 최대값 `Gmax` + 여유 이내.
- **주의(자기 채점 방지)**: 튐 지표는 "화면 속도 > 750cm/s"인데 M3은 화면 속도를 직접 제한한다. 그래서 튐 지표만으로 판정하지 않는다. Jerk, 수렴 시간, 화면-서버 차이, 영상을 함께 본다. `Vc`(300)는 지표 임계값에서 역산하지 않고 고정한다.

## 8. 확인할 위험

- `SmoothClientPosition_Interpolate`의 virtual 여부, 오프셋 필드(`MeshTranslationOffset`) 접근 방식은 엔진 헤더로 먼저 확인한다.
- 패킷 순서가 뒤바뀌어 **오래된 상태가 나중에 오는지**: 타임스탬프 복제 후 `ServerStateTime`이 줄어드는 보정이 있는지 센다. 있으면 그런 보정은 무시하는 규칙을 M1에 넣는다(엔진이 이미 버리는지도 확인).
- 스무딩을 늘리면 화면이 서버보다 더 늦는다. 이 트레이드오프를 숨기지 않고 표로 보여 준다.
- 측정은 PIE 단일 프로세스다. 최종 수치 몇 개는 별도 프로세스(01 문서 7.2)로 재확인한다.

### 9.1 사전 확인 (배치 `B1123-2255`, Linear 재측정)

- 타임스탬프 복제 확인: `ServerStateTime` 0 없음(1417/1417), 줄어드는 값(순서 뒤바뀜) 0, 같은 값 3. 순서 뒤바뀜 처리 규칙은 지금은 필요 없다(같거나 작은 값은 지터 계산에서 건너뜀).

| 그룹 | 가설 | 조건 × 방식 | 보는 지표 |
|---|---|---|---|
| J (문제 정의) | 평균 지연이 아니라 지연의 흔들림 폭이 튐을 만든다. 폭이 어느 값을 넘으면 기본 스무딩이 튀기 시작한다 | 평균 200ms 고정, 폭 0~300ms: `L200, J190-210, J175-225, J150-250, J125-275, J100-300, J50-350` × `Exp, Ada-T` | 튐/분 vs 폭, 큰 보정 직후 화면 최대 속도 p95 |

### 10.4 M3 정리 (기존 데이터)

M3 단독(Ada-R, 따라잡기 150cm/s)은 J100-300 튐 11/분으로 줄었지만, M3은 화면 속도를 직접 자르므로 튐 지표(속도 > 750)를 스스로 맞추는 구조다(6절 주의). M2와 함께 켠 Ada는 Ada-T와 차이가 없었다(J100-300 21.5 vs 22.7/분). 즉 M2가 이미 보정 직후 속도를 낮춰서 M3이 자를 구간이 거의 남지 않는다. 실제로 제한이 걸린 프레임은 Ada(M2+M3, 따라잡기 300cm/s)에서 0.1~0.3%, M3 단독(150cm/s)에서 J50-150 28%·J100-300 42%였다(두 판의 따라잡기 속도가 달라 엄밀한 비교는 아님) → 제안 방법에서 뺀다.

## 11. 최종 발표 준비 (2026-11-27 오후)

### 11.1 튐 모델과 관계식 (`Scripts/Analysis/rubberband_relation.py`, 결과 `Saved/Tasks/20261127-rubberband-relation`)

모델: 보정 크기 D를 시간 상수 τ로 메우면 보정 직후 화면 속도는 대략 v + D/τ다. 튐 기준은 1.5·v_max = 750이므로 **D/τ > v_max/2 = 250cm/s이면 튄다.** 따라서 튀지 않으려면 τ ≥ D/250이어야 한다.

- 보정 12.2만 건(같은 프레임에 온 보정은 합침). D/τ 구간별 실제 튐 확률은 1.6%(0~50) → 17%(200~250) → 50%(400~500) → 63%(700~)로 단조 증가한다.
- 벡터 모델 |v + D벡터/τ|: 예측 속도가 1000을 넘으면 86~97%가 튀고, 600 미만은 2~4%만 튄다. **실제 튐 프레임의 83%는 직전 0.1s 안에 예측 속도 > 750인 보정이 있었다.** 예측 정밀도는 63%다.
- 보정 크기 p95 ≈ 300cm/s × 도착 간격 p95(지터 조건). 즉 D ≈ 0.6·v_max·g이고, τ ≥ 2·0.6·g ≈ 1.2·g다.
- 필요 τ와 추정 지터 J: τ = 0.06 + k·max(0, J − 10ms)에 맞추면 **보정 95%를 막는 k ≈ 4.8, 99%를 막는 k ≈ 7.6**이다. 실험한 k=6(튐 18/분)은 그 사이, k=12(1.9/분)는 99% 선 위다. 지터가 10ms 미만이면 필요 τ(0.03~0.05)가 기본 0.06보다 작다 → 데드존과 기본값 유지가 데이터로 정당화된다.
- J50-350에서는 필요 τ99 = 0.27이 상한 0.25보다 크다 → k만 키우면 상한이 걸린다(K 그룹에서 m0.30으로 확인).
